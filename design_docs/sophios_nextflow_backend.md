# Sophios Nextflow Backend — Locked Design

This document governs the Nextflow backend.

---

## 1. Governing rule

> A workflow is either fully lowered into a validated executable Nextflow model, or compilation fails with an actionable diagnostic.

Sophios never emits a partially supported workflow and never silently changes source semantics. A rendered TODO, retained metadata, plausible-looking script, successful preview, or hand-built intermediate representation is not evidence that a source workflow is executable.

This rule outranks feature breadth and schedule. When a source construct has no approved lowering and is not one the Sophios compile alone uses (§3), the compiler rejects it before artifact generation.

---

## 2. Product boundary

Sophios supports Nextflow DSL2 as a target alongside CWL. The backend has four responsibilities:

1. lower the supported subset of a compiled Sophios workflow, read through its resolved view, into an executable Nextflow model;
2. render deterministic inspectable artifacts from that model;
3. read back exactly the DSL2 the renderer writes, as the renderer's inverse, and import it as one Sophios workflow, stopping on anything else (§4.2); and
4. expose the supported behavior through the existing Python, CLI, and later service boundaries.

The backend reads the core compiler's `WorkflowGraph` through its resolved view (`docs/dev/architecture.md`), never the CWL Sophios writes; that design is the successor that changes the substrate from CWL. The view is a read-only reading of the graph: the sources of each step input at its level and through call boundaries, its record fields and the type it delivers, the parsed `when`, `scatter`, workflow inputs and outputs with the run's values, each tool step's inherited requirements, and the run policy. It has no meaning of its own: a construct Sophios took from CWL means what CWL v1.2 says, with cwltool the reference, and what Sophios invented is resolved before it. Tools stay CWL: the view carries each tool's document, and the backend reads it as before. The backend does not repeat link resolution, inference, or composition; for each construct the view states it decides how to express it in Nextflow, or refuses it. The CWL target, its inliner and its rewriting flags are untouched by this backend. This private seam may evolve without changing the public Python API or the backend's semantic contract.

The backend does not perform a second forward inference pass. An imported workflow (§4.2) writes every edge itself, so compiling it relies on no inference.

### Non-goals

- General Groovy parsing or execution equivalence for arbitrary `.nf` files.
- Silent preservation of unsupported semantics in executable output.
- Running a generated pipeline other than as one local `nextflow run` child process (§4.4), and setting an executor or any other Nextflow option for the user: each reaches Nextflow only as an unchecked passthrough argument. A compute service runs the service form (§4.5), the pipeline written for Singularity without its record, under its own contract; Sophios only writes it.
- Nextflow-native graph inference, until a successor design. The backend does not perform a second forward inference pass.
- Backward compatibility for private, unversioned intermediate Python objects. Serialized schemas are versioned explicitly.
- User-written Nextflow configuration. The generated `nextflow.config` is the only configuration Sophios supports.
- User-written Groovy in a workflow compiled to Nextflow. `target="nextflow"` has no Groovy passthrough; the gate under which one could ever be admitted is stated in §6, Expressions.

## 3. Closed-world capability contract

Every source feature considered by the backend is classified as exactly one of:

| State | Meaning |
|---|---|
| **Lowered** | Has an approved lowering, executable-model representation, renderer implementation, and real-runtime evidence. |
| **Compile-time** | Sophios uses it while compiling; the Nextflow output carries nothing for it, and the generated pipeline's execution does not depend on it. |
| **Rejected** | Produces a structured diagnostic before executable-model construction, and no artifacts. |

Imported text is a separate matter (§4.2): the reader admits exactly the text the renderer writes, and anything else stops the import with a coded diagnostic. That is a property of imported text, not a state a Sophios/CWL field can be in.

The backend's support is one table in code, `src/sophios/nextflow/support.py`. It gives every Sophios/CWL field the backend considers one of the three states, keyed by its `cwl_utils` class as before; capability analysis takes the fields it consumes from it, and the user documentation is rendered from it. The table is the authority for which state a field is in; this document is the authority for what each state and each lowering means. Moving a field into **Lowered** or **Compile-time** is a revision of this design before it is a change to the table.

Capability analysis is closed-world. Each semantic source field is consumed by a lowering, used by the Sophios compile alone, or reported as rejected. Unknown requirements, bindings, expressions, directives, operators, and executable syntax are never ignored.

Diagnostics identify the user's file and line, the step, the rejected construct, and the next supported action when one exists; each is an error diagnostic with an `nf-sNNN` code, printed in the layout of every other Sophios diagnostic (`docs/dev/architecture.md`); a tool's field is named by its path inside the tool's own document, and no diagnostic names a path into the CWL Sophios writes. Capability analysis aggregates independent findings so users do not have to fix unsupported constructs one at a time.

## 4. Architecture

### 4.1 Forward export

```text
Python Workflow or .wic
  -> Sophios compilation (once): WorkflowGraph and the tool each step runs
  -> resolved view: the graph, each tool step's document, the run's values, the outputs kept
  -> closed-world capability analysis over view constructs and tool documents
  -> semantic lowering
  -> validated ExecutableNextflowWorkflow
  -> deterministic renderer
  -> JSON IR, workflow.nf, nextflow.config, nextflow_params.json
```

Unsupported input exits through structured diagnostics before executable IR or artifacts exist. The view takes each tool step's document from the compile's tools; the compile emits nothing, and no pass reads a workflow's emitted CWL.

### 4.2 Import

```text
workflow.nf, nextflow_params.json, nextflow.config
  -> reader: the renderer's inverse
  -> validated ExecutableNextflowWorkflow, the one compilation produced
  -> one Sophios Workflow, built through the public Python API
```

The import reads the three files Nextflow itself reads: `workflow.nf`; `nextflow_params.json`, which holds the job values; and `nextflow.config`, which names the container engine the pipeline is written for (§4.5). It never reads `nextflow_workflow.json`, which is a record of the model (§7), not an input.

**The subset is the renderer's output.** The reader admits exactly the text the renderer writes (§7) for a valid model, and nothing else; it is not a reader of general DSL2. The only freedom is layout. In `workflow.nf` and `nextflow.config` it is indentation, the length of each run of spaces and tabs between tokens on a line, blank lines, line and block comments, the order of the top-level process blocks, and the line ending, a line feed or a carriage return and a line feed, which Groovy reads alike even inside a triple-quoted script; none of them applies inside a string literal, a script or stub body, or a helper definition. Space where the renderer writes none, or none where it writes some, is content. In `nextflow_params.json`, which is read as JSON, the freedom is JSON's own: its whitespace and the order of an object's keys. Everything else is content: a line break, since Groovy ends a statement at one, and the order of the statements in `main:`, since the call order is the order of the steps. Each generated helper `def` must appear byte for byte as rendered; an edited helper is outside the subset, however small the edit.

**The reader is the renderer's exact inverse.** From the three files written for a model it returns that model, and rendering it gives the same text up to layout. Process scripts parse back into the model's typed command tokens; no script is kept as shell text. There is no structural representation between the text and the model (§5.1), and nothing is retained opaque. A field the text shows only through others is derived from them, and the reader checks that the text agrees: the float-to-text helper on exactly the references a float parameter reaches, the engine enabled exactly when a process has a container, and the like. The orders the text does not show are canonical in the model (§5.2). The reader reads every form the renderer writes (§4.5): it renders the model again for the engine `nextflow.config` names, Docker's `docker.enabled` or Singularity's block, and with the record of the outputs (§7) when the entry workflow prints it, and the text must be that rendering. A pipeline with outputs that an earlier release wrote, which recorded each output from the work directory and published nothing, is outside the subset: compile it again.

**Anything outside the subset stops the import.** A construct the renderer does not write — an edited helper, a directive, operator or declaration of its own, a hand-written script, a parameter the entry block does not check — is a coded diagnostic (`docs/error_codes.md`) naming the construct and its line. There is no partial import, no warning that lets the import go on, and no opaque region.

**The import builds one Sophios workflow.** From the model, the import builds one Sophios `Workflow` through the public Python API a user writes: a `CommandLineTool` made a step for each process, the parameter values bound on workflow inputs (§4.3), and every edge bound explicitly on the input it feeds, a carried input bound as a `StepInput` on a name its tool does not declare, the steps in the workflow block's call order, which is a topological order. It never builds CWL: producing CWL is the CWL backend's work, `Workflow.compile()`, and a `.wic` file is `Workflow.write_wic`'s. The imported workflow relies on no inference, which is an authoring convenience, not something an import leans on: compiled to Nextflow with inference disabled, it gives back the model the reader returned. The import checks this by compiling the workflow it builds: a pipeline no workflow built through the API compiles to as it is written stops the import with its own code (`wic054`) at the process or workflow it names. One such is a name the compile would change, such as a capitalized process name, which normalization never writes; another is a port of a CWL tool named like an attribute of the tool builder's `Inputs` or `Outputs`, such as `keys`, which the builder has no spelling for.

**Carriers.** A fact the Sophios workflow needs, that no Nextflow directive acts on and that the rest of the text cannot supply, is written into its process's `ext` directive under its CWL name. Nextflow keeps a task's `ext` values and acts on none of them; only a script that reads `task.ext` sees them, and no generated script does. Runtime proof against the pinned Nextflow, under the v2 parser, shows each carrier below parsing, running, and changing nothing. There are three:

- `cudaVersionMin` and `cudaComputeCapability` of a `cwltool:CUDARequirement`, as written; cwltool's schema requires both, with no null. The `accelerator N` directive stays as it is.
- `Directory`: the names, in output order, of the process's outputs whose CWL type is `Directory`. A `path` output declares no kind, and Nextflow's `type: 'dir'` is not enforced for a literal output name, with or without `glob: false`, so it would read as a check without being one.
- `WorkflowStepInput`: the names, in order, of the process's inputs its tool does not declare: the step-only inputs the lowering carries (§6, Step inputs). Each is a `val` input the command never reads, which the text writes as it writes the tool's own `val` inputs, so only the carrier tells the two apart. The reader requires it to name exactly the process's last `val` inputs, in order (`wic053` otherwise); a process without it has no step-only inputs, so a pipeline written before the carrier existed still reads.

Another carrier is admitted only by a revision of this design that names it and shows both conditions. `ext` holds nothing the rest of the text states, and is never a copy of the model.

**Losses.** The import is exact on the model, not on the Sophios source the model came from. What the lowering does not keep does not come back; each loss is documented, not diagnosed:

- original names: normalization (§6, Nested namespacing) makes `~`, `@` and every character Nextflow does not allow `_`, and gives a reserved, capitalized or script-declared name a leading `_`; the import keeps the Nextflow spelling, a leading `_` included, and normalization is idempotent, so a second round trip is exact;
- nesting: subworkflows are inlined (§6, Topology), so the import is one flat workflow;
- labels, docs, the other compile-time fields (§3), and Sophios-only hints;
- a step-only input the lowering does not carry: one fed only by root workflow inputs and read by neither the step's `when` nor its `scatter` (§6, Step inputs);
- `cudaDeviceCountMax`: the import writes the `accelerator` count N as `cudaDeviceCountMin`, since N is what both runners request;
- comments and formatting;
- every choice that lowers to the same model: where a value came from — a tool's default, a step's default, an unbound optional input and a value written on a step each become a workflow input named `<step>_<port>` holding the value, and a step's default beside a source becomes a `merge_nested` step input with `pickValue: first_non_null` over that input; a maximum resource, read as the count it lowered to; `dockerImageId`, read as `dockerPull`; whether a requirement was a hint; a plain `$(inputs.<name>)` of a File or Directory input, read as `$(inputs.<name>.path)`, which CWL reads as text wherever it stands; `type: stdout`, read as a `File` output globbing the `stdout` name; whether a token came from an argument or an input's own binding, and its binding position; a single-input scatter's `scatterMethod`; the spacing, parentheses and string quotes of a `when`, its `===` and `!==`, read as `==` and `!=`, a unary `+`, which side of a comparison `null` is on, and `!(x == null)`, read as `x != null`; whether adjacent `shellQuote: false` texts were one binding or several; and a tool's input order, which the model makes canonical (§5.2).

**Verification.** The renderer and the reader encode one subset, so the forms with holes — those the renderer fills with names, values or other forms — are one table both use: the renderer fills it and the reader matches it, and the two cannot drift; the helpers are already one shared text. Each hole is read once: it holds the longest text that the form's text up to the next hole follows, and the reader never goes back to try a shorter one, so a line is read, or refused, in time linear in its length, however nearly it matches a form. The renderer writes every form so that it reads back this way but one, a conditional output's channel `ch_<process>_<emit>`, which splits more than one way when a name holds a `_`: the reader fills that form for each process output and looks the name up, and the statement that defines the channel takes the name as one hole. Conformance is a fixed point over the image of compilation: for every Sophios workflow the target compiles, with its job values bound in Python or given by an inputs file, to a model M, the three files written from M import to a workflow that compiles to M again. Equality is of models, which implies equality of the text and also sees the fields that never reach it; the domain is what compilation produces, not every model the constructors accept. A declared list of layout transformations, each with its reason, leaves the result unchanged. One mutation of generated text per import diagnostic raises that diagnostic, with its line, and imports nothing. The import reads the three files alone: no tool registry, no network, and no look at a path a parameter names.

### 4.3 Public boundary

The intended Python surface is:

```python
workflow.compile()                                 # CompiledWorkflow
workflow.compile(target="cwl")                     # CompiledWorkflow
workflow.compile(target="nextflow")                # CompiledNextflowWorkflow
workflow.compile(target="nextflow").write(outdir)  # the four artifacts (§7), for Docker, in outdir
```

A value bound on a workflow input, `workflow.inputs.<name> = value`, is that input's value in the job a compile produces, as an inputs file gives one: `compile()` carries it in `cwl_job_inputs`, and the Nextflow target in the parameters. One compile operation is sufficient. Its Nextflow result holds the executable IR as `nextflow_workflow` (§5.2) and every note the compile made, the core compile's then the lowering's, in `diagnostics`, and it writes itself as `CompiledWorkflow.write()` does: `write(path=None)` writes the four artifacts into the directory `path`, the current directory by default, returns that directory and compiles nothing again. It overwrites the four and removes nothing; the CLI and a run remove them first, so there a workflow the lowering rejects leaves none from an earlier write. Duplicate convenience methods are not part of the target design. The compile, and a run from Python (§4.4), lower the resolved view built with the values bound on the workflow's inputs and, for a workflow that declares outputs, with only those outputs kept, and not the step outputs Sophios exposes under their made names: the same workflow `compile()` returns for the CWL target, passed to the view's builder rather than edited into CWL dicts. `workflow.check(target="nextflow")` does the same lowering in memory, then the machine checks of a run (§4.4, Check), as `--check` does, and writes nothing of its own: it returns the notes without printing them, and raises what the compile raises, and a `SophiosError` for what this machine lacks.

A run takes the target as a CWL run takes its runner options (§4.4):

```python
workflow.run(target="nextflow")               # RunResult
workflow.start(target="nextflow")             # RunHandle
await workflow.run_async(target="nextflow")   # RunResult
```

The intended CLI surface is:

```text
sophios --yaml workflow.wic --target nextflow
```

`--target nextflow` is sufficient by itself. With `--run_local` Sophios runs the pipeline, with `--generate_run_script` it writes the command that runs it to `run.sh`, and with `--check` it checks the machine for it (§4.4); these three, `--passthrough_flags`, `--outdir`, the output folder the pipeline publishes into, and `--container_engine`, which the pipeline is written for (§4.5), act under either target, and every option only a CWL run reads is rejected under `--target nextflow`. A compile under `--container_engine singularity` writes the four artifacts for Singularity. Nested workflows are inlined from the view (§6, Topology); a construct on a workflow-call boundary or a child workflow is lowered or rejected by name before the boundary is crossed. `--partial_failure_enable` and its two code options are CWL options, so they are rejected under `--target nextflow` like every other; the view carries the run policy, and the backend rejects partial failure by construct as well, which is how a Python workflow compiled with `policy=RunPolicy(partial_failure=True)` is refused.

Import (§4.2) is exposed from the concrete `sophios.api.python.nextflow` module. The removed generic API aggregator is not restored.

### 4.4 Running

Sophios runs a generated pipeline through the run mechanism of its CWL runners. The backend registered for the target `nextflow` and the runner `nextflow` answers the questions every backend answers (`design_docs/sites-design.md` §6), and Sophios starts what it launches as one child process on this machine, then streams, stops and reports on it as it does a CWL runner.

- **Check.** Each File or Directory input value, as the CWL pre-flight checks it (`wic016`), except an output-target `Directory`, which prepare makes for a run; the `nextflow` program, which must start (`nextflow -version`) and so find a Java it can run; the output folder, which must be writable, as the CWL pre-flight checks it (`wic021`); and, when a process has a container, the runner's container engine, which the generated configuration enables, Docker or Singularity, checked as the CWL pre-flight checks an engine; which processes have a container it reads from the three files prepare wrote, through the reader (§4.2), as the import does. The program is found as a CWL runner is: for `--generate_run_script` on PATH, where `run.sh` calls it, and otherwise in this Python environment first; on Windows the run is sent to WSL, since Sophios conducts a run on POSIX only. A missing or failing program is `wic029`, an engine that cannot run containers `wic015`, whose message names `--container_engine`, which both targets take, and no option only a CWL run takes. The pipeline still checks its input values itself when it starts (§6, Inputs and channels). `--check` stops after it; the artifacts it read were written into a temporary directory that is now removed (Prepare).
- **Prepare.** The workflow is lowered from its bound values, each relative File or Directory path made absolute against the directory it is read from (the `.wic` file's on the command line; from Python, the working directory, or the config's `relative_to` when it gives one), and the four artifacts (§7), the pipeline written for the runner's container engine with its record, are written to `nextflow_<workflow>/` in the base path, with `nextflow_names.json` beside them giving the Sophios name of each process and workflow output by its Nextflow name. The directory is the workflow's own, as a CWL run's `<workflow>.cwl` and `<workflow>_inputs.yml` are, so runs of two workflows started together from one base path each read and run their own pipeline, and a run's outcome reads its own names. Each output-target `Directory` input — one a tool writes into through a writable `InitialWorkDirRequirement` entry and captures as a `Directory` output, found as the CWL path finds it — whose path names nothing yet is made, empty, since the pipeline stages it as an input and the CWL path has its runner make it. The lowering's notes are reported as a run reports its notes, and real-time analyses are written as for a CWL run. A check (`--check`) writes all of this into a temporary directory instead, removed when the check ends, and makes no output-target `Directory`, so it leaves the base path as it found it, as a CWL check does.
- **Launch.** `nextflow -C <dir>/nextflow.config run <dir>/workflow.nf -params-file <dir>/nextflow_params.json -work-dir <dir>/work -output-dir <outdir> -ansi-log false`, then the passthrough arguments, started in the workflow's directory `<dir>`, `nextflow_<workflow>/` in the base path, with the environment a CWL runner gets: this process's, with the run's variables on top, and `NXF_SYNTAX_PARSER=v2` over both, since the pipeline stops under any other script parser (§6, Inputs and channels). `-C` makes the generated configuration the only one Nextflow reads, so no configuration file in the base path, the working directory or the user's home takes part. Nextflow's own log and cache, `.nextflow.log` and `.nextflow/`, are in that directory with the pipeline they belong to. `<outdir>` is the run's output folder, as a CWL run's: the config's or `--outdir`, made absolute, or `outdir_nextflow_<workflow>_<time>` in the base path, which the local run path names for every runner; the run's result names it as its `outdir`.
- **Outcome.** A run that exits 0 reports the workflow's output object, read from the record the pipeline prints (§7): each workflow output under its Sophios name, a `File` or `Directory` as a CWL object with its `class`, `location`, `path` and `basename`, a captured text as a string, `null` for a null, and the output of a scattered step as an array. It is written to `output_<workflow>.json` in the base path, as for the CWL runners. Its paths are the copies the pipeline published into the output folder (§4.5), and each file also stays in the run's work directory, which `-resume` reads. A run that fails reports each process its log names as `Error executing process`, by its Sophios step name, with the exit status Nextflow gives for it, or none when it gives none, as for a missing output.
- **Real-time analysis** does not run beside a Nextflow run: an analysis watches cwltool's job directories, and a Nextflow run has none. The run says so in one line and goes on without it.
- **Options.** An executor, and every other option of `nextflow run`, reaches Nextflow only as the run's passthrough arguments, unchecked, as the CWL runners' own options reach them, after `run <dir>/workflow.nf`; an option of the launcher itself, which goes before `run` (`-log`, `-q`, `-D`, `-bg`, `-syslog`, `-trace`), cannot be passed. They are given on the command line after `--passthrough_flags yes`, and from Python as the flags of `Nextflow(...)`, handed over as written with Nextflow's one dash. What an executor does with the tasks is that executor's contract, not a claim this backend proves. A configuration file or `-stub-run` passed this way is not supported: Sophios supports neither user-written configuration (§2) nor dry runs (§7).

### 4.5 Publishing, the container engine and the service form

Every pipeline the renderer writes publishes the workflow's outputs into one folder, the output folder, and is written for one container engine, the runner's: `Nextflow(container_engine=)`, `docker` by default or `singularity`, and on the command line `--container_engine`. The renderer takes the engine and whether to print the record of the outputs (§7); nothing else in the text differs between the forms. Another engine is refused, naming the two, where the pipeline is written, and on the command line before anything is written, as a usage error. A local run and a compile write the record, in the form that replaces what the output folder holds under a copy's name; a compute service (`docs/compute.md`) reads the outputs from what Nextflow prints, so the compute client asks for the pipeline for Singularity without the record, the service form, and sends it as one file whose parameters are those `nextflow_params.json` holds, every path as written. The service runs it with the only configuration the run reads, its own, and deletes the work directory when the run ends.

- **Engine.** `nextflow.config` enables the engine when a process has a container: `docker.enabled = true`, or `singularity { enabled = true; autoMounts = true }`, the line the compute service writes; false when none has. Under Docker a process with a container clears the image's entrypoint and runs its command after the entrypoint's words, which its `beforeScript`, on the host where the task starts, writes into the task directory after pulling the image if it is missing. Under Singularity a process with a container has its `container` directive and, when it asks for GPUs (`accelerator`), `containerOptions '--nv'`; no `beforeScript` and no `--entrypoint`. Singularity's `exec`, which Nextflow runs a task with, runs no `ENTRYPOINT`, so there is nothing to clear. The script runs the command after the image's runscript, `/.singularity.d/runscript`, with `SINGULARITY_NO_EVAL` set: that is what `singularity run --no-eval`, the CWL runners' way, executes, since the runscript Apptainer writes for an image then execs the image's `ENTRYPOINT` words and the command's with no shell evaluation. An image with no runscript runs the command alone. Under Singularity every task's script first sets `HOME` to its task directory, as CWL makes it the designated output directory, and a tool's own `HOME`, an `EnvVarRequirement`, after it: Nextflow runs a container without the user's home, whose path the image holds read-only, so a tool that writes under its home would fail there. Runtime proof runs the script Nextflow generates against the runscript Apptainer wrote for a real image, in a Linux container, and shows the command's words reaching the entrypoint as given, `$`, quotes and spaces included; it runs no Apptainer, so that a cluster runs the image is the service's contract, and a local run under Singularity is proven only for a pipeline with no container.
- **Outputs.** The entry workflow publishes each workflow output (`publish:` and an `output` block) as one value, the one its record (§7) carries, with each path in the output folder, placed once every output has completed as Toil places a CWL run's: a path inside a folder the workflow also returns is at its place in that folder's copy, never copied on its own, and every other path is copied once, the outputs in the order of their names, under the first name no copy has taken, its own, then the name and `_2`, `_3` and on, a path copied already given its one copy. So the pipeline first copies each path no other returned path holds, and then gives every path its place. Nextflow publishes a path already in the output folder as it is: measured on the pinned Nextflow, it needs no `workflow.output.mode`, and the folder holds copies, never links. Its own publishing would place each file at its path in its task's directory, so two files of one name, from two outputs or from the tasks of a scattered one, would meet, one of them lost or the run failed after its tasks, and a file globbed in a subfolder would land in it. The object `-output-format json` prints is then the run's outputs laid out as a CWL run's: a `File` or `Directory` as `{"class", "path"}`, an array for a scattered output, a captured text as it is, and `null` for a null. A null never binds a channel, so an output that is null leaves its channel empty instead, which Nextflow prints as `null`. A local run gives `-output-dir` its output folder (§4.4); a pipeline run by hand without one publishes into `results/` in the folder Nextflow starts from (measured). Nextflow's own copy writes into the folder as it finds it (measured): a file of an output's name is replaced, a folder of an output's name gets the new copy inside it, and a third run into the folder fails after its tasks, the nested copy's name taken. A local output folder may exist and hold files, so the form that records its outputs (§7), which a local run runs, first deletes what the folder holds under each copy's name, a folder and all in it, or a link but not what it names, and leaves the rest: a run into the folder of an earlier one publishes as the first did, run after run, and under `-resume`, which runs no task again and copies every output again (measured, three runs, a file and a folder among the outputs). The service form deletes nothing: the compute service takes only a missing or empty folder, and that form's text is fixed (§4.5, the service form). In the recording form each path also carries its own name as its `basename`, which a local run reports, as cwltool reports a renamed copy's; the compute service reads Nextflow's object, whose path names the copy, and reports the copy's name. Runtime proof against the pinned Nextflow, in the service form and in a local run under Singularity, publishes a file, a text, a null, a scattered array of output folders, a scattered file in a subfolder whose output's name sorts before that of another file of its name, a file two outputs return, a folder with a file of that name in it, which an output whose name sorts before the folder's returns too, and a file of the folder's name, whose output's name sorts between those two, and finds each path in the output folder, placed as a CWL run places it; a local run of that workflow, three times into one folder, the third with `-resume`, finds the same paths each time, each reported by its own name; the example workflows run locally under Docker find each output, published, by its own name; the compute client's service lane runs outputs of one file name, and a folder holding one, on Toil and on Nextflow and finds the same copies.
- **Names.** The object Nextflow prints names each output by its Nextflow name, and a client that attaches to a run it did not submit has no names file (§4.4). A workflow output whose name normalization (§6, Nested namespacing) changes, such as `Result`, published as `_Result`, is therefore refused in the service form with `wic061`, naming it; every other output's Nextflow name is its Sophios name. A workflow that declares no output returns its steps' outputs, each named `<step>~<port>`, which normalization always changes: each is refused, its message saying to declare the outputs to return. A local run reads its names file, so it refuses neither.
- **Import.** The reader (§4.2) reads every form back, the engine from `nextflow.config` and the record from the entry workflow; the service form, which is sent alone, reads back beside the configuration the renderer writes for Singularity. The service form's text for one workflow is a golden file, compared byte for byte.

## 5. Intermediate representations

### 5.1 No structural representation

Nextflow source has no structural representation. The reader (§4.2) goes from the three files straight to the executable representation below, and stops on what that cannot hold; nothing is parsed into a looser form to be inspected, kept opaque, or promoted later.

### 5.2 Executable `ExecutableNextflowWorkflow`

The executable representation contains only fully lowered Nextflow semantics. Its constructors are validated and its values are deeply immutable.

Conceptual components include:

- typed workflow parameters with explicit presence/default state;
- typed process input and output ports;
- typed command tokens that distinguish literals, input references, and any approved shell operators;
- typed output capture and glob templates;
- typed resource and container directives;
- typed connection variants for workflow input, process edge, and workflow output; and
- unique normalized process, port, parameter, and emit identifiers.

Nullable process endpoints, magic directive keys, raw CWL expressions, mutable collections inside frozen records, and unclassified executable fragments are not valid executable-model states.

Orders the rendering does not show are canonical, so two models the renderer writes alike are one model, and the reader returns it (§4.2): processes are in the order the workflow calls them, a stable topological order; a process with a multi-input scatter declares its scattered inputs first, as its tuple renders them; and connections are in the order of their destination process and port, with the workflow outputs after them in the order they are emitted. None of these orders carries meaning. Two forms the rendering writes alike are canonical the same way: adjacent raw shell literals are one, joined by a space, and a `when` is held as one tree of those its Groovy writes alike, with `==` and `!=` for `===` and `!==`, no unary `+`, `null` on the right of an equality, and `x != null` for `!(x == null)`; with operands typed as the subset types them, each pair means the same (§6, Expressions).

Connection variants make boundary-to-boundary dangling edges unrepresentable. Keyed output collections and post-normalization validation make duplicate emits unrepresentable. A workflow parameter feeding multiple ports is valid only when every sink agrees on how the parameter's channel is built: its qualifier, its path kind, and whether it carries a list. The parameter's declared type (§5.3) fixes the channel the renderer builds for it; one definition computes the construction a sink needs, and the graph validator holds every sink to the declared type's, so the channel the renderer builds is the one the validator compared. A source of a step input's idioms (§6, Topology) takes the parameter's own value. A scatter adapter (§6, Inputs and channels) belongs to the scattered process and takes no part in the comparison: a scattered input carries its whole array, so one array parameter may be scattered at one step and consumed whole at another.

### 5.3 Serialization

Serialized IR declares a schema version and representation kind. It is a record of the model, written beside the pipeline (§7), and nothing reads it back: there is no hydration. The import (§4.2) and a run's check (§4.4) read the three files Nextflow reads.

The schema is not stable until it meets users, so it promises no compatibility yet. Any change to the serialized form bumps the schema version, and serialization always writes the current version.

The model records each workflow parameter's declared type, which the entry check (§6, Inputs and channels) reads.

## 6. Semantic lowering contracts

### Expressions

**Expression handling admits two closed classes and nothing else.** A CWL expression is representable in the executable model only when it is a *static projection* or a member of the *safe JavaScript subset* below. A static projection is a finite path into a known data structure, decided entirely at compile time from the CWL source text, where every step has a provably identical Nextflow counterpart; it involves no computation. No expression text of either class reaches the executable model or the generated pipeline. Any other form — string manipulation, and any arithmetic, comparison, conditional, operator, or function call outside the subset — is not representable and fails closed. A form whose Nextflow counterpart is *close but not exact* is not representable either: the divergence is never repaired by compensating logic, because that logic would itself be unapproved computation.

The approved projections are `$(inputs.<name>)`, its spelling `$(inputs.<name>.path)` on a File or Directory input, which lowers to the same reference and is admitted on no other input, and `$(inputs.<name>.basename)` in template positions (§6, Commands; §6, Outputs and globs), and the two `outputBinding` capture declarations in §6, Outputs and globs. Each is one closed literal shape recognized by exact match against frozen data in the compiler, never by a grammar that could be widened a case at a time, and widening the set is a revision of this design. Recognizing a shape is not the same as understanding a language: the compiler matches admitted projection text and rejects everything else, and outside the safe subset's parser no code path inspects, transforms, or composes expression text.

A lowering's own fixed rendered idiom is not the computation this rule forbids. The Groovy conditional a boolean flag renders to, the per-item join an array binding renders to, the float-to-text idiom a float reaches a command through (§6, Inputs and channels), and the size and encoding preconditions the file-text capture renders to are each part of one mapping, chosen once at design time and identical for every workflow. What the rule forbids is deriving Groovy from CWL expression text by any route other than the safe subset's typed nodes, and repairing a mapping that does not already agree. A precondition that makes the generated pipeline fail exactly where CWL fails is the fatal-error half of a mapping, not a repair of one; a transform that massages a value into agreement *is* a repair, and disqualifies the projection outright.

**Arbitrary JavaScript is ruled out, not deferred.** This is deliberately a narrower claim than "no JavaScript". Sophios is built on CWL, whose only syntax for arithmetic and conditions is the JavaScript expression, and useful workflows depend on both; so the backend admits that syntax for the safe subset below, and for nothing else. Sophios does not evaluate JavaScript in any form: not at compile time, not at runtime, not by embedding a JavaScript engine, not by shelling out to `node`, and not by translating JavaScript outside the subset into Groovy. Nor does anything evaluate in the renderer, which §7 fixes as a pure transformation of the executable model. The reasons are structural rather than practical. Evaluation breaks §3's closed-world contract, because an evaluated expression's result space cannot be classified in advance. It breaks §5.2's and §7's prohibition on opaque strings, because the expression text would have to survive into the executable model in order to be evaluated later. It makes generated pipelines non-self-describing, because the emitted `.nf` would no longer say what it does. Shelling out to `node` adds a container runtime dependency, which §6, Resources and containers requires evidence for. And it is the same category as arbitrary Groovy equivalence, which the non-goals refuse. The subset escapes each of these reasons by construction rather than by exemption: compile-time typing classifies its result space, typed nodes replace its text before the executable model exists, and its one fixed Groovy rendering says exactly what it does. This is recorded as a decision rather than a deferral so that it is not re-litigated as one: admitting arbitrary JavaScript requires a successor design document, not a revision of this one.

**User-written Groovy is ruled out today, and gated if it ever comes.** Three decisions, recorded here so they are not reopened piecemeal. First, `target="nextflow"` has no Groovy passthrough: a workflow carries no user-written Groovy in any position, and the backend admits none. Second, JavaScript and Groovy never coexist in one workflow. That is a statement about what the user writes — the CWL expression syntax of the safe subset on one hand, Groovy on the other — never about the Groovy the backend generates from the subset, which is compiler output and unaffected. Third, if Groovy passthrough ever comes to this backend, it comes only for workflows that use neither `when` nor `scatter`: those two constructs follow CWL semantics and need JavaScript, so a workflow that uses either has passthrough blocked up front rather than reconciled case by case. Admitting passthrough at all is a successor design, in the same posture as arbitrary JavaScript above; this paragraph fixes the shape it would have to take.

**The safe JavaScript subset (approved lowering).** Every expression the subset admits has exactly one meaning, identical under JavaScript — the CWL reference path, where `node` evaluates it — and under its fixed Groovy rendering. The subset is parsed at compile time against the closed grammar below into typed executable-model nodes; an expression the grammar or the typing rules do not admit is rejected with a diagnostic naming the construct.

- *Position.* A step's `when`, and nowhere else. Every other expression position keeps the projection rule, `valueFrom` on a command-line binding or `arguments` entry included, so a computed `valueFrom` there is rejected by name, and the executable model has no token for one (§5.3). `valueFrom` on a workflow step input is rejected by name in any form.
- *Form.* The whole field is one `$( … )` parameter reference. `${ … }` function bodies, and an expression interpolated into surrounding text, are rejected.
- *Literals.* Numbers; `true` and `false`; `null`; strings in double or single quotes containing printable ASCII and no backslash.
- *References.* `inputs.<name>`, where the input is a `boolean`, `int`, `float`, or `string`, optional or not. The name is a step input, declared by the step's tool or not. It carries the type of the value the step input delivers, optionality included, as the resolved view gives it: a `when` reads the step input's value, which CWL does not convert to the tool's type before it evaluates the `when`. A step input the step does not bind is rejected by name. No other property access; `self` and `runtime` are rejected.
- *Operators,* with JavaScript precedence and parentheses: unary `!`, `-`, `+`; `*`, `/`, `%`, `+`, `-`; `<`, `<=`, `>`, `>=`; `==`, `!=`, `===`, `!==`; `&&`, `||`. The conditional operator, `**`, bitwise and assignment operators are rejected.
- *Calls.* `Math.abs`, `Math.sqrt`, `Math.floor`, `Math.ceil`, `Math.round`, `Math.pow`, and `Math.min` and `Math.max` over two or more arguments. No other call is admitted.

Typing is checked at compile time and is what makes JavaScript and Groovy agree. An optional reference has type T-or-null. It appears only as an operand of `==` or `!=` against `null` (either spelling of equality); every other operator rejects it by name. JavaScript would coerce an absent value — `null + 1` is `1`, `!null` is `true` — and the `[]` sentinel would not, so the coercion is not representable. A guard such as `inputs.n != null && inputs.n > 3` is rejected with it: `&&` does not narrow, and admitting the guard means defining that narrowing. Arithmetic operators and `Math` calls take and give numbers; `+` never concatenates strings. Ordered comparisons take two numbers. Equality otherwise takes two operands of the same type — number, boolean, or string; with operands typed this way `==` and `===` coincide, so both spellings are accepted. `!`, `&&`, and `||` take and give booleans, so neither language's short-circuit value can be a non-boolean. There is no truthiness: a `when` must be boolean-typed.

Every number is an IEEE-754 binary64 value on both paths, as it is in JavaScript. `int` values are converted, so integers are exact only within ±2^53. `/` is always true division. Numbers are always finite: an evaluation in which any subexpression becomes NaN or ±Infinity — division by zero, `Math.sqrt` of a negative, overflow — fails with a diagnostic naming the step, the field, the authored expression in its canonical form (§5.2), the subexpression that became non-finite, and the input values it read. This deliberately diverges from the CWL path, where JavaScript carries the value on: a comparison with NaN is quietly false there, so a condition quietly skips its step, and a quiet skip is far harder to debug than a named failure. `Math.pow` renders as `StrictMath.pow`: Java's `Math.pow` is only within 1 ulp and may be intrinsified, while `StrictMath.pow` is the fdlibm the CWL path's `node` uses. `Math.sqrt`, `Math.floor`, `Math.ceil`, and `Math.abs` are exact on both sides and render as `Math`. `Math.round` rounds half toward +∞ and is rendered by a fixed idiom exact over the whole binary64 range, since Java's `Math.round` saturates at the `long` range. Nothing else rounds, truncates, or wraps. The runtime that executes the rendering is the pinned one: Nextflow 26.10.5 on Temurin 17.

Two authorities must agree here — JavaScript and the Groovy rendering — so conformance is a differential property rather than a set of examples: generated in-subset expressions and input values are evaluated by `node` and by the rendered Groovy under the pinned Nextflow, in one batched run. Every expression whose JavaScript evaluation keeps each subexpression finite must agree; every other expression must fail with the non-finite diagnostic. Source-to-runtime cases additionally compare the generated Nextflow run with the CWL reference runner. Widening the subset — a new operator, call, type, or position — is a revision of this section.

Declaring `InlineJavascriptRequirement` is not itself the use of JavaScript, so a tool that declares it and then uses only approved forms stays legal — the same shape of decision as `ShellCommandRequirement` with no `shellQuote: false` binding, which changes nothing to render (§6, Commands). The requirement is a capability declaration; the violation is a non-admitted form. A later change must not "fix" this by rejecting the declaration.

### Commands

CWL command construction is normalized before rendering. Ordering follows the pinned CWL version, including defaults and tie-breaking. Command parts remain typed as literal data or interpolation references; quoting is decided per token or segment, never by scanning a completed string for `$`.

A `$` that is not followed by `(` or `{` in a literal `arguments` entry or `baseCommand` is plain text, as in CWL: it is a literal segment, and the shell-quoting helper passes it to the command as that character. A `shellQuote: false` literal, which no helper quotes, may not hold a `$`: the task's `bash -ue` would expand it in the task's environment, not CWL's `sh -c` in its own.

**Boolean flags (approved lowering).** A `boolean` input with an `inputBinding` and no `valueFrom` lowers to a typed conditional flag token that references the input by name and carries a non-empty prefix. At runtime, `true` renders the shell-quoted prefix as exactly one argv word and `false` renders nothing; a boolean binding without a prefix contributes nothing for either value. Flag tokens are valid only in command token position — never in globs or stream targets — and only against `val` ports. An optional boolean lowers the same way whether a value is present or absent: a flag token never dereferences its channel value, only tests it, so the absent-optional `val` lowering below covers this case directly and an absent optional boolean renders identically to `false`.

The rendered flag is a conditional over its channel value, so the lowering is sound only when that value is a JSON boolean at runtime. Capability analysis therefore requires every input consumed by a flag token to resolve to a boolean-typed source, whether that source is a workflow input or a producing process output port. Truthiness of a staged path or of a string such as `"false"` must never be allowed to decide a flag.

### Inputs and channels

File and Directory inputs lower to path semantics. The JSON scalar types `string`, `int`, `float`, and `boolean` lower to value semantics; `long` and `double` are rejected with a diagnostic naming the type, since the safe subset's number rules (§6, Expressions) do not cover them. Defaults are explicit model values. Missingness is distinct from JSON `null`.

**Workflow input values are checked at entry.** The generated pipeline checks every workflow input value against its declared type when it starts, before any process runs, as cwltool rejects an invalid job value before it runs anything. The check goes by the value's runtime type, because the pinned Nextflow's v2 script parser, its default, gives a command-line value and a params-file JSON string the same type, a string, and keeps nothing that says where a value came from. The v1 parser (`NXF_SYNTAX_PARSER=v1`) converts a command-line value itself, `--name 010` arriving as the integer 10, which the check could not tell from a number, so the entry workflow's first statement stops the run under it, before any process runs, saying the pipeline needs the v2 parser. A value that already has the declared type passes, for a `float` an integer or a finite double; a params-file number with a point or an exponent given for a `float` converts as Float text below says. A string given for a `boolean`, `int`, or `float` converts only when its text is exact: `true` or `false` for a `boolean`, integral text within the `int` range for an `int`, and finite float text for a `float`. A `File` or `Directory` value is path text, or a mapping with a `path` (a CWL File or Directory object, which only the params file can give); a mapping that has a `class` passes only when it is the declared type. The path text passes when it is not empty and Nextflow's `file(…, glob: false)` names an entry of the declared kind there: `isFile()` for a `File`, `isDirectory()` for a `Directory`. Array and record values come only from the params file. `[]` stands for an absent optional value and passes for an optional `boolean`, `int`, `float`, or `string`; for an optional `File` or `Directory` it stops the run, since no path parameter has a lowering of it (absent-optional inputs below), so compilation rejects an absent optional `File` or `Directory` workflow input, whether a step reads it or not, naming the input. Any other value stops the run with a diagnostic naming the parameter. The check is the fatal-error half of the mapping, not a repair of it: it converts nothing that is not exact, so a flag, a `when`, or a value port never sees a value of the wrong type.

**Float text (approved lowering).** A float reaches a command — by a plain `$(inputs.<name>)` reference, a binding, an optional binding, or as an item of an array binding — as Python's `str()` of the value: the shortest digits that read back as the same binary64 value, of those the nearest to it, and of two equally near the one with an even last digit; in decimal notation when 1e-4 ≤ |x| < 1e16, with `.0` after an integral value, and otherwise in scientific notation, a mantissa, `e`, a sign and an exponent of at least two digits, as `1e-07` and `1.5e+16`; and `-0.0` for negative zero. The float-to-text idiom renders it: one fixed helper, emitted once and only into a pipeline that renders a float, exact over the whole binary64 range, in the posture of `Math.round` (§6, Expressions). From one significant digit up, it rounds the value's exact binary expansion down and up to that many digits, keeps the candidates `Double.parseDouble` reads back as the value, and takes the nearest; then it formats the digits as Python does. The JDK's `Double.toString` is not a counterpart: under the pinned JDK 17 it is not shortest for every double (JDK-4511638, fixed in JDK 19), its notation thresholds and exponent spelling differ, and a user may run another JDK. An integer that reaches a `float` input, given in the params file as a JSON integer or joined into a `float` array from an `int` source, keeps its integer text, Python's `str()` of the integer. cwltool is deliberately not followed here: the pinned cwltool reads every job value and tool default through ruamel, and its `Builder.tostr` writes a float as `Decimal` of its YAML or JSON spelling, rounded to an integer by `quantize(1)` where that `Decimal` shows an exponent; only a float interpolated into a longer template goes through `str()`. It therefore keeps a spelling that is not shortest, `1.50` as `1.50`, and changes the value of a float spelled with an exponent, `1e-07` to `0` and `1.0e+16` to `10000000000000000`, so on the job file the CWL target writes the two targets print the same text only for zero and for 1e-4 ≤ |x| < 1e16. Reproducing that would print a value other than the one given.

The pinned Nextflow reads a params-file number with a point or an exponent as a `BigDecimal`, which has no negative zero, and a whole number outside the `int` range as a `long`, wrapping one outside the `long` range. Sophios therefore writes every value of a `float` parameter into `nextflow_params.json` as its Python text, which the entry check converts exactly, sign included, and the reader reads that text back as the model's float. A number written into the params file by hand passes for a `float` as Nextflow has read it, and converts exactly: a `BigDecimal` by `BigDecimal.doubleValue`, which rounds correctly, and a `long` as its own integer. Nextflow's reading loses two things before the check sees the value: the sign of a zero, so a hand-written `-0.0` reaches the command as `0.0`, and the value of a whole number outside the `long` range, which wraps; nothing the check holds tells either from an exact value, so stopping on them would stop every `0.0` and every whole number outside the `int` range too. The documentation says so and gives the text form, `"-0.0"`, that keeps such a number exact. Text given on the command line converts as it always has, only when it is exact. A non-finite value stops the run at the entry check. Two authorities must agree, Python and the rendered helper, so conformance is a differential property: generated doubles — random bit patterns across the exponent range, subnormals, every power of two and of ten, the 1e-4 and 1e16 boundaries and their neighbours, integral and many-digit values, the extremes and `-0.0` — are written by Sophios and rendered through one generated pipeline under the pinned Nextflow in one batched run, and every one must equal Python's `str()`; in the same run, hand-edited JSON numbers that Nextflow reads exactly must equal Python's `str()` of the JSON value, and command-line text Python's `str(float(text))`, and workflow inputs joined by a step input's `linkMerge` or referenced in a glob must reach the command as Python's `str()` too.

**Absent-optional `val` inputs (approved lowering).** An absent optional value lowers to a reserved empty-array sentinel `[]` carried by a `Channel.value(...)` element — one element, never zero — so the channel always terminates and a receiving process can observe the exact value it received. Runtime proof ruled out the naive representation: `Channel.value(null)` never binds under the pinned Nextflow runtime, so the process that consumes it never starts and the run hangs indefinitely — a literal JSON `null` is not a terminating channel value here, whatever CWL's own null means. `[]` is Groovy-falsy like `null` and `false`, so a flag ternary treats it identically, and it is unambiguous within this lowering's scope because this lowering never applies to an array-typed port: no scalar (`string`/`int`/`float`/`boolean`) value is ever legitimately an array, so this sentinel can never collide with a genuinely empty array under the array lowering below. This is sound only where nothing dereferences the value unconditionally: interpolating the sentinel into a plain template segment (`.toString()` on a Groovy list) renders `"[]"`, not a clean absence signal. The lowering is therefore scoped to `val`-qualifier inputs whose consuming tool port is either never referenced in that tool's command tokens, stream targets, or output globs, or referenced solely as the boolean-flag token it drives — both positions already treat their value as a condition rather than dereferencing it, so the sentinel renders safely as falsy. Every other reference position — a plain value interpolation anywhere in a command token, stream target, or glob — keeps rejecting an absent optional source; the presence-gated value binding is not approved. Absent-optional `path` (File/Directory) inputs also keep rejecting: `path`-qualifier channel construction always stages its value unconditionally, so a safe representation needs its own runtime-proven convention, and none is approved. An absent-optional array-typed input is likewise out of scope for this lowering.

Channel construction considers all consumers. Connection order never selects a qualifier or staging policy.

**Array-typed inputs (approved lowering).** A CWL array input — `{type: array, items: <scalar>}`, where `<scalar>` is `File`, `Directory`, `string`, `int`, `float`, or `boolean` — lowers to a port carrying the same qualifier its item type would carry alone (`path` for File/Directory items, `val` for scalar items), plus an explicit array marker. Whether a sink carries a list is part of the one-parameter rule (§5.2), so a parameter that one sink takes as one scalar and another as a list is rejected. Cardinality is otherwise a channel-construction concern, not a new qualifier, and both forms are runtime-proven: a `val` array is a JSON list flowing through `Channel.value(...)` exactly as any other JSON value; a `path` array is a single `Channel.value(...)` element holding a Groovy list built with `file(...)` per element, so Nextflow stages every element for one process invocation rather than fanning the channel out over several. Nextflow hands a `path` input holding exactly one file to the script as a bare `Path`, which has no list operations, so every array-typed `path` port declares `path <name>, arity: '0..*'`, whether a workflow input feeds it, it sits outside a scattered tuple, a gather fills it, or a step input joins it: runtime proof against the pinned Nextflow shows that range delivers zero, one, and many files as a list, which is what the array binding's emptiness test and per-item join read. Every such port also stages each file in its own numbered directory, as cwltool does, so same-named files from different directories never collide; Nextflow otherwise stops the task with an input file name collision. An array-typed input is referenced only by an array binding, which reads the staged paths, so the directory changes nothing else. An empty array is a present, valid, zero-length value — distinct from the absent-optional lowering above, which represents no value at all and is out of scope for array-typed ports entirely; this lowering never emits or accepts the absent-optional sentinel for an array port, so the two representations cannot collide.

**`InitialWorkDirRequirement` entries (approved lowering, one supported shape).** A `listing` entry names one File or Directory input: the bare shorthand expression `$(inputs.<name>)`, or a `Dirent` whose `entry` is that same bare reference and whose `entryname` is absent, the self-referencing `$(inputs.<name>.basename)`, or a literal string with no expression and no path separator. The entry's CWL name is that literal, or the input's own basename otherwise, and `writable`, when present, is a literal boolean. Every entry stages its input under a hidden name the backend reserves, and the task makes the entry under its CWL name before the command runs: a copy when `writable: true`, so the command may change the entry without touching the staged input, and a symlink otherwise. An entry under the input's own basename that is not writable is made this way too, not left to Nextflow's own staging: Nextflow leaves a task's staged inputs out of a pattern output's matches, while a CWL glob matches the entry as it matches any file in the output directory. Such a port carries a typed entry marker, the CWL name when it is a literal and whether the entry is a copy, and the renderer emits the hidden staging name and the command that makes the entry. The marker replaces the `stage_as` rename. The port's own value is the hidden staged file, not the entry. A reference to an input whose entry keeps the input's own basename — plain, `.path` or basename in a command token, and in an output glob or a stream target as `docs/nextflow.md`, Basename references, admits it — names the entry, as cwltool maps the input's path to its entry; that is the shape of a tool that writes into a writable output directory and captures it with `glob: $(inputs.<name>.basename)`. Such an output directory is a `Directory` input like any other, so it must exist when the pipeline starts; Sophios's CWL path makes one given as a bare name, and the generated pipeline does not. An input whose entry has a literal name may not be referenced anywhere in that tool's command tokens, stream targets, or output globs: the supported pattern is for the command to address the entry by the name the CWL author already chose, hard-coded directly into `baseCommand`/`arguments`. Each claim — the copy is independent of the staged input, the symlink resolves to it, a pattern glob matches the entry, and the entry exists before the command runs — is admitted only with runtime proof against the pinned Nextflow.

**Required channel adapters (approved lowering).** Scatter is the only approved topology whose two ends disagree about channel cardinality: a scattered process consumes one element per task where an unscattered one consumes a whole value. Lowering represents that with a typed adapter on the scattered input's connection, drawn from a closed set in the executable model. Every scatter, single-input included, is indexed: the scattered inputs' whole-array value channels are combined, each boxed in a one-element list so `combine` carries the array rather than splicing its elements, and one `flatMap` turns the whole arrays into a queue of `[index, elements…]` invocations — by index under `dotproduct`, the adapter a single-input scatter receives, and as every combination under the crossproducts. The process takes the index as a hidden `val` beside its inputs and returns it with its outputs, and a `gather` adapter on the process edge out of the scatter sorts by it (`toSortedList { it[0] }`) and strips it, so a gathered array is in invocation order whatever order the tasks finish in. A process has one adapter: every scattered input of one process carries the same one. The adapter is a property of the scattered process, not of the workflow parameter, so it leaves the parameter's channel-construction comparison (§5.2), and connection order never selects channel behavior.

The closed set is widened only by the fixed whole-array idioms of §6, Topology: `dotproduct`, `flat_crossproduct` and `nested_crossproduct` on a scattered input's connection, whether its whole array comes from a workflow input, from a gathered output, or from an unscattered step's output, and `gather` on a process edge out of an indexed scatter. Pairing or crossing two queue channels and every other operator remain rejected with a named diagnostic rather than approximated. The approved set is closed data in the executable model, so the renderer maps an adapter to its idiom and can neither widen nor infer one.

### Outputs and globs

Every output has a concrete capture mechanism. Support includes path globs and declared stdout/stderr file capture. Primitive outputs are not represented as bare variable names. A rendered glob remains a glob at run time: a name assembled from runtime data is still pattern-interpreted, so a staged name carrying a glob metacharacter does not match the file the process wrote. Rendering an assembled name literally is a distinct lowering, because it changes emitted bytes and the reader (§4.2) with them.

Supported glob expressions are parsed into typed literal and input-reference components. Raw CWL expression strings cannot enter the executable model.

Beyond the glob, `outputBinding` capture behavior falls into three statuses this section keeps distinct, because they are not the same kind of "no":

- **Approved.** The two `outputEval` capture declarations below, each one exact literal text under a literal-glob restriction.
- **Ruled out on the record.** Evaluating any other `outputEval` text, which would require the arbitrary JavaScript evaluation §6, Expressions permanently refuses; `outputEval` is not a safe-subset position. These are not awaiting a lowering.
- **Rejected with a known relaxation path.** An approved capture declaration paired with a wildcard or input-reference glob, whose gate is stated below as a specific proof obligation.

`secondaryFiles`, record-typed outputs, array-typed outputs, and expression forms in a workflow output's `outputSource` remain rejected with no approved lowering.

**Output cardinality declaration (approved lowering, one supported literal).** An `outputBinding.outputEval` whose text is exactly `$(self[0])` — surrounding whitespace trimmed, no tolerance for internal variation — is recognized as a *cardinality declaration*, not as an expression: it states that the port carries one value rather than a list. It lowers to a closed capture marker on the output port, mirroring the array marker on input ports, and no `outputEval` token of any kind enters the executable model. On a required output, the marker renders as Nextflow's `glob: false, arity: '1'` options on the `path` output (an optional one declares `arity: '0..*'`): the first makes the approved CWL literal remain literal even when it contains a Nextflow-only pattern character such as `{`, `}`, or `\`, and the second is runtime-proven against the pinned Nextflow to emit a single path value rather than a list and to fail the task when nothing matches. The reader (§4.2) reads `glob: false` beside an arity back as the same closed capture marker.

The declaration is admitted only when the paired `glob` is one literal containing no wildcard character — no `*`, `?`, or `[` — and no input reference. `self[0]` means "the first of the matched list", so projecting it is provably identical only where the match set has exactly one member by construction, and a literal glob names at most one filesystem entry. A wildcard glob would instead make the two runtimes' glob match *ordering* load-bearing, and that ordering is unproven. An input-reference glob is rejected for the same reason one step removed: its runtime value could itself contain a wildcard, so wildcard-freedom is not decidable from the source text. The restriction lives in the executable model rather than only in capability analysis — a capture marker beside a non-literal or wildcard-bearing glob is an unrepresentable state, so no later change can reach it by a different code path.

**Relaxation path for wildcard globs.** Admitting `$(self[0])` against a wildcard glob is a gated extension with known requirements, not a dead end. A future contributor must demonstrate that CWL's glob match ordering and Nextflow's are identical, covering at least the cases where they could plausibly diverge: filenames of differing length, mixed upper and lower case, numeric suffixes where lexical and numeric order disagree (`part2` against `part10`), and the locale sensitivity of the collation each runtime's underlying glob implementation uses. Absent that proof the two runtimes may silently select *different files* for the same workflow with no error raised anywhere, which is exactly the failure mode §1 forbids; the restriction therefore stands until the ordering is proven rather than assumed. The same proof would unlock the input-reference glob, whose only defect is that it cannot be shown wildcard-free at compile time.

**File-text capture (approved lowering, one supported literal).** `loadContents: true` paired with an `outputEval` of exactly `$(self[0].contents)`, on an output declared `type: string`, under the same literal-glob restriction as the cardinality declaration, lowers to a closed file-text-capture marker: the port becomes a value port whose value is the named file's decoded text. Both halves are required and neither is admitted alone — `loadContents` without that `outputEval` is rejected, that `outputEval` without `loadContents: true` is rejected, and the pairing on any output type other than `string` is rejected.

**The sink of a captured value.** A file-text-capture output's only approved sink is a workflow output. A process-to-process edge out of one is rejected with a named diagnostic, for a reason that is about the model rather than about this lowering: apart from this lowering every process output carries the `path` qualifier, so a process edge could not disagree with its destination port about channel semantics, and the executable graph has no source-to-destination qualifier agreement check to lean on. Relaxing this means adding that check — the process-edge analogue of the workflow parameter consistency rule in §5.2 — and proving a captured value feeding a downstream `val` port at runtime. That is a self-contained relaxation, not a redesign, and without it the restriction stands. The restriction is enforced in the executable model as well as in capability analysis, so no other code path can reach the combination.

**Cardinality and scatter.** The capture marker is per task and scatter's cardinality is per collection, so the two compose without overlap. `arity: '1'` says each task of a process produces one matching file; the single-input scatter lowering (§6, Topology) says how many tasks run. A scattered step over N elements therefore runs N tasks, each producing one file, and its output queue channel carries N single-file elements — exactly the array-typed workflow output CWL declares for a scattered step whose tool output is a single `File`. The marker needs no scatter-specific case, and the scatter contract's rules for a scattered step's outputs (§6, Topology) apply unchanged. This is the model's first output-cardinality concept, and it deliberately does not attempt to restate the collection cardinality scatter already owns.

### Topology

The executable graph validates endpoint existence, direction, multiplicity, acyclicity where required, unique emits, normalized-name collisions, and workflow-boundary consistency before rendering.

**Single-input executable scatter (approved lowering, one supported shape).** A step whose `scatter` names exactly one input — the string form, or a one-element list — lowers to that input's port receiving one element of the source array per task through the `dotproduct` adapter above, so the process runs once per element while its remaining inputs stay value channels and broadcast to every task. Multi-input scatter is rejected, and with it every case where `scatterMethod` is load-bearing: `dotproduct`, `flat_crossproduct`, and `nested_crossproduct` all describe how two or more scattered arrays combine, which the multi-input scatter lowering below decides. At exactly one scattered input all three coincide — one task per element, output nesting depth one — so a `scatterMethod` carrying one of those three values alongside a single-input `scatter` is consumed as an inert restatement instead of rejected; the compiler emits `scatterMethod: dotproduct` unconditionally, so rejecting the field outright would put executable scatter out of reach of the public Python and CLI surfaces and out of reach of the real-fixture runtime proof this document requires. Any other `scatterMethod` value is rejected by name.

The scattered input's source must be exactly one array-typed workflow input whose item type carries the same qualifier and path kind as the scattered port itself. The gathered output of an upstream scatter is also admitted as that source, under the gather lowering below, and the output of an unscattered step, taken as one value under the collection cardinality rule below; a wildcard-glob array output still cannot carry an array, so scattering over an array-marked port stays rejected for the same reason nested arrays are.

**Collection cardinality.** A scattered step's output port carries one value per task, not one value overall. The gather lowering below delivers those values as the one array CWL gives a workflow output or a downstream input, in invocation order. An output of an unscattered step reaches a scattered step as one value (Nextflow's `.first()`), both as an input broadcast to every task and as the array the step scatters over. An unscattered process emits exactly one element per output, so taking the first element is exact. Nextflow emits a value channel from a process whose inputs are all value channels, which is the common case because every workflow input is one; there `.first()` changes nothing, and Nextflow warns that it is useless. A process emits a queue channel when one of its inputs is a queue, such as a conditional step's output; without `.first()`, that one-element queue paired with the scatter's queue would silently truncate the run to one task instead of N. The backend applies `.first()` to every unscattered source rather than tracking which channels are queues, since a wrong guess truncates the run and the warning costs nothing. The second use needs an unscattered step with an array-typed output, and array-typed tool outputs stay rejected (§6, Inputs and channels), so no unscattered step produces an array a step can scatter over until a lowering for array-typed outputs is approved.

**Nested workflows (approved lowering).** A step whose compiled `run` is itself a `Workflow` lowers by inlining, at any depth. The backend inlines from the resolved view (§2), which keeps the nesting: the view's tool steps at every depth come with each source resolved through the call boundaries it crosses, a nested workflow's input to whatever the outer step binds it to and a reference to the outer step's outputs to the inner endpoint that subworkflow output's `outputSource` names, and with each tool step's compiled step id. The backend takes those steps and ids as they are; the core compiler's graph is not flattened, and nothing rewrites the CWL Sophios writes. Its own work is the capability checks below, which see every call and the nested workflow it runs before a boundary is crossed (§4.3). Inlining is chosen over emitting a nested DSL2 `workflow` block: every executable connection variant addresses a process endpoint, so a subworkflow call would introduce a new endpoint kind across the graph validator, the renderer, and the reader at once, while inlining reaches the same observable execution — the same tasks, the same data flow, the same output files — with no new endpoint kind at all. Inlining is never a source-language decision in the renderer, and it is not silent: the emitted artifacts are flat by construction, so the composition structure lives in the source workflow and in the process names, not in the generated DSL2.

Composition findings are resolved before the rest of capability analysis, because the flat graph every other pass analyzes cannot be built while its composition is unsupported. Composition findings still aggregate among themselves across every nested step.

**Nested namespacing.** Each inlined step is named by its compiled step id, which the core compiler makes: a step's id as written, less a `.wic` suffix, with `@<position>` added when another step in its workflow, or one of that workflow's inputs or outputs, has the same id; a nested step's id is joined to those of the steps that call it with `~`, outermost first and at any depth. The backend takes that id as it is and normalizes it. Two instantiations of one subworkflow therefore cannot collide at any depth, and the normalized-name collision check applies to the namespaced names rather than to the inner ones, naming both colliding ids as written.

**Subworkflow I/O.** Every declared subworkflow input must be bound by the outer step's `in`, and every name in the outer step's `out` must be a declared subworkflow output; an unbound input or an undeclared output is rejected rather than defaulted. Nested input and output definitions are subject to the same closed-world per-port field checks as the outer workflow, so a field the outer workflow rejects, such as `secondaryFiles` or a workflow output's `linkMerge` and `pickValue`, cannot disappear during inlining. Each subworkflow output must carry exactly one `outputSource` resolving to one of that subworkflow's own step outputs: a subworkflow output that forwards one of its inputs is rejected, exactly as boundary passthrough is rejected at the outer boundary. An inner step's sources resolve either to another inner step's output or to a subworkflow input, which the outer binding replaces; anything else is rejected by name.

**Step inputs.** A step input's `default`, `linkMerge` and `pickValue` are each lowered by one fixed Groovy idiom over the step's bound values, chosen once and identical for every workflow, with no JavaScript; `docs/nextflow.md` states each idiom and what is rejected. A source that may be null joins a list only beside a `pickValue`, and a `pickValue` or a `default` over an array source is rejected, since the `[]` sentinel for a null array is the value of a genuinely empty one. Each idiom is admitted only with runtime proof against the pinned Nextflow.

**Step-only inputs (approved lowering).** A step input the step's tool does not declare is passed to no tool, as in CWL, but the step's `when` and `scatter` see it and the step starts only once its sources have values. The lowering carries it as an input of its process, after the tool's own: a `val` input, never a `path`, so nothing is staged for it, which the process block declares and the command never reads, named in the process's `WorkflowStepInput` carrier (§4.2), whose channel the call passes as it passes every other input. A process starts only when every input has a value, which is CWL's wait; a conditional call merges and branches over it, and a scattered one broadcasts it, as each does for the tool's own inputs, and a process whose tool declares no input has one to gate on. One lowering choice is fixed: a step-only input whose sources, resolved through every call boundary, are all root workflow inputs, and that neither the `when` nor `scatter` reads, is not carried, since root workflow inputs have values from the start and nothing reads it, so it cannot change what the step does or when it starts. `scatter` over a step-only input is rejected by name, since no process port receives the element. The lowering is admitted only with runtime proof against the pinned Nextflow that a carried input read by a `when`, and one fed by a step output, each run as cwltool runs them.

**Multi-input scatter (approved lowering).** A step may scatter two or more inputs under `dotproduct`, `flat_crossproduct`, or `nested_crossproduct`. Each scattered source arrives as one whole array — a workflow input, the gathered output of an upstream scatter, or an unscattered step's output taken as one value (collection cardinality above) — and the invocations are computed from the whole arrays by one fixed Groovy idiom per method, never by channel operators whose pairing depends on arrival: `dotproduct` pairs by index and fails on unequal lengths, `flat_crossproduct` enumerates the product with the first declared input outermost, the CWL reference order, and `nested_crossproduct` enumerates the same invocations and keeps each one's position in every dimension.
A single-input scatter lowers through this same lowering, as one scattered input under `dotproduct`, where all three methods coincide. Every invocation carries its index as a hidden leading value through the scattered process's inputs and outputs, and a gather sorts by it, so output order never depends on task completion order. An empty scattered array produces zero invocations. Unscattered inputs broadcast to every invocation as value channels. Whatever the number of scattered inputs, an unscattered input comes from a workflow parameter, from a gathered upstream output, or from an unscattered step's output taken as one value (collection cardinality above), so each broadcasts as one value and nothing pairs a queue with the scatter's queue.

**Gather.** A scattered step's output feeds a downstream array-typed input once, as one array in invocation order. A gathered `path` array is delivered to its consumer as a list however many files it holds, one included (§6, Inputs and channels). That gathered array is the only process-produced array admitted as a scatter source: array-typed tool outputs stay rejected (§6, Inputs and channels), and one from a wildcard glob would also need proof that CWL's and Nextflow's glob match orders agree. A `nested_crossproduct` result has one array dimension per scattered input and is admitted only as a workflow output; a downstream nested-array input is rejected by name, so the array marker keeps meaning exactly one dimension.

**Conditional steps (approved lowering).** A step's `when` is a boolean-typed safe-subset expression (§6, Expressions), evaluated once per invocation — once per combination under scatter — after the step's inputs are bound. It reads every step input, the ones the tool declares and the step-only ones alike. A true condition runs the process. A false condition runs no task, and the step's outputs are `null`, as in CWL: never absent, because an absent value would let a downstream step run under CWL and silently not run under Nextflow.

`null` is carried by the reserved `[]` sentinel the absent-optional `val` lowering (§6, Inputs and channels) already uses, so the backend has exactly one representation of a CWL `null`. The rendering evaluates the predicate over each invocation's bound inputs and splits the invocations on it: the true branch feeds the process, the false branch emits the sentinel in place of each output, and the two are merged back into the output channel in invocation order. Every skipped invocation therefore emits exactly one element per output, so channels terminate and downstream completion cannot hang. Under scatter the gathered collection keeps the sentinel at each skipped position, which is CWL's array with `null` at that position. That array is not itself null, so the admission rule for a possibly-null value does not cover it. The gathered output of a conditional scattered step reaches a workflow output only, where each inner sentinel stands for `null` (nothing in the generated pipeline rewrites it, so the emitted array carries `[]` at each skipped position); that claim is admitted only with runtime proof against the pinned Nextflow. Every other consumer of it, re-scattering included, is rejected with a named diagnostic.

### Resources and containers

Only explicitly mapped directives are executable. Unsupported requirements and hints are diagnosed rather than ignored. Text rendering is not runtime proof; CPU, memory, environment, and container claims require runtime proof.

## 7. Renderer and artifacts

The renderer accepts only `ExecutableNextflowWorkflow`. It is a pure deterministic transformation and makes no source-language decisions.

It does not:

- inspect raw CWL;
- reinterpret opaque strings;
- infer channel behavior from connection order;
- consume magic metadata keys;
- emit semantic TODOs;
- skip unsupported fields; or
- downgrade a compiler diagnostic into a comment.

For a valid executable model, rendering is total. Unsupported-user-input errors belong to capability analysis; renderer invariant failures are compiler defects.

Dry runs are not supported. Every generated process carries a `stub:` block that prints that Sophios-generated Nextflow does not support dry runs (`-stub-run`) and exits 1, so a dry run stops at its first task: a process with no stub block would run its real command under `-stub-run`. The block is part of the fixed rendering of every process, and the reader (§4.2) requires it as rendered: a process without it is outside the subset.

The entry workflow publishes every workflow output (§4.5) and, written with the record, records each for the run that reads it back (§4.4): once every output has been published, it prints one line on standard output per output, `sophios-output ` and then the JSON array of the output's Nextflow name and its published value. A path is an object with its `class`, `File` or `Directory`, its absolute `path` in the output folder, written as its text, since Groovy's JSON writer would walk a path as the list of its names, and its own name as its `basename`, whatever name its copy took; a captured text is a string; the `[]` sentinel (§6, Topology) is `null`; and the output of a scattered step is the array of its values in the order its workflow output emits them, with one array level per scattered input under `nested_crossproduct`. The outputs are recorded together when the run has finished, not each as it completes. One helper, emitted only when the workflow has an output, makes the published value, in one of two forms: with the record, it replaces what the output folder holds under a copy's name and gives each path its `basename`; without it, the service form's, it does neither (§4.5). The two share their first line, so the reader (§4.2) takes a `def` that is either, byte for byte, and requires the publishing, the record when there is one, and the helper of that form as rendered. The service form prints no record (§4.5).

The artifact set is:

| Artifact | Contract |
|---|---|
| `nextflow_workflow.json` | Versioned, validated executable IR: a record of the model, which nothing reads back (§5.3). |
| `workflow.nf` | Deterministic DSL2 generated solely from executable IR. |
| `nextflow.config` | Deterministic supported configuration, the container engine's line (§4.5); the only Nextflow configuration Sophios supports. |
| `nextflow_params.json` | Deterministic serialized workflow parameters. |

Repeated rendering is byte-stable and does not mutate its input.
