# Partial failures

How do I keep a workflow going when one of many scattered jobs fails? By
default a CWL runner stops the workflow at the first failed step, and a step
that scatters over a hundred inputs fails when one of them does. With
`--partial_failure_enable`, Sophios rewrites the compiled CWL so that a failing
job counts as a success with no output, and every later step runs on what it
was given and skips what it was not.


`fail.cwl` exits non-zero with the probability it is given, so some of the
eleven scattered jobs fail on most runs. Compiled and run as it is, the
workflow fails with them. With partial failures:

```bash
sophios --yaml test_rand_fail.wic --run_local --partial_failure_enable
```

the run completes, and `echo` runs once for each job of `fail` that
succeeded.

## What the flag changes in the compiled CWL

Two things, both visible in `autogenerated/`:

- Every tool gets `successCodes`, so that the exit codes you name count as
  success, and each of its outputs whose type is written as a string becomes
  optional: `string` becomes `string?`, `File[]` becomes `File[]?`, and a
  type already ending in `?` is left alone. An output whose type is written as
  a mapping (`{type: array, items: File}`) or a list is not changed, and stays
  required. A job that fails with one of those codes then ends with its
  outputs `null` rather than failing the step.
- Every step with required inputs gets a `when:` over them that runs it only
  when they are not `null`, replacing any `when:` it had:

```yaml
- id: echo
  in:
    message:
      source: fail/fail__failout
  scatter:
  - message
  when: $(inputs["message"] != null)
```

A step whose input came from a failed job is therefore skipped, and its own
outputs are `null` in turn, so the skip propagates down the chain and no
further. A step with several inputs runs only when all of them are present.

The codes that count as success are `0` plus those you name:

- `--partial_failure_success_codes 1 2` lists codes;
- `--partial_failure_success_codes_range 1 5` names a range, lower bound
  included and upper bound excluded.

Both default to `0` and `1`, so with the flag alone an exit status of `1` is
a partial failure and anything else still fails the step. Give a tool's real
failure codes; a code that means a crash should stay a failure.

## What to expect

- cwltool warns, for each step that reads from one with a `when:`, that
  the source may produce `null`. With the flag every step has one, so the
  warning repeats; it is expected and changes nothing.
- A tool's own expressions are not rewritten. An `outputEval` that reads
  `self[0].contents` fails on a job that wrote nothing, even though the
  command's exit code was forgiven; write such expressions to return `null`
  when `self[0]` is missing, as the [developer guide](dev/devguide.md) shows.
- A plain CWL workflow under `--allow_raw_cwl` cannot take the flag, since
  Sophios compiles nothing to rewrite.
- `--cwl_inline_subworkflows` leaves a call nested when the flag added a
  `when:` to it.
- The flag is a command-line option. `Workflow.run()` has no partial-failure
  setting; write the workflow out with `write_wic()` and run it on the
  command line.

## What it is not

Partial failures do not retry a job, and do not make a workflow succeed that
produced nothing: a step with no surviving input is skipped, and a workflow
whose every job failed ends with empty outputs. The runner's output
(`output_<workflow>.json`) shows `null` where a job failed, which is how you
find out what was lost. For a tool that may legitimately fail and whose
failure a later step should see, give it a `successCodes` of its own and let
it write a marker output instead.
