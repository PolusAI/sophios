# Partial failures

When a step scatters over a hundred samples and one of them fails, a CWL
runner stops the whole workflow, and the ninety-nine good results go with
it. This page shows you how to keep going instead: with
`--partial_failure_enable`, a job that fails counts as a success with no
output, and every later step runs on what it was given and skips what it was
not. You need [scatter](scatter-and-conditions.md) to follow it.

## An example

`test_rand_fail.wic`, one of the examples Sophios copies to `~/wic/examples/`,
scatters a tool that fails on purpose:

```{literalinclude} tutorials/test_rand_fail.wic
:language: yaml
:caption: test_rand_fail.wic
```

```{literalinclude} tutorials/fail.wic
:language: yaml
:caption: fail.wic
```

Read it as three steps. `array_float` makes a list of eleven numbers, from
0.9 to 1.0. `fail.wic`, a [subworkflow](subworkflows.md) with one step, runs
`fail.cwl` once per number, scattered over its input `with_probability`, and
`fail.cwl` exits with status 1 with the probability it is given. So nearly
every one of the eleven jobs fails, which is the point: it stands in for a
scatter over a hundred real samples, a few of which are bad. Then `echo`
prints whatever each job produced. Run as it is, the workflow stops at the first failure:

```bash
sophios --yaml ~/wic/examples/test_rand_fail.wic --run_local
```

```text
...
WARNING [job fail] exited with status: 1
WARNING [job fail] completed permanentFail
WARNING [step fail_2] completed permanentFail
ERROR Workflow cannot make any more progress.
WARNING Final process status is permanentFail
Failure! step 'fail' exited with status 1. Its own messages are above, under its name.
```

With the flag:

```bash
sophios --yaml ~/wic/examples/test_rand_fail.wic --run_local --partial_failure_enable
```

every job of `fail` is logged `completed success` whether its command was
`true` or `false`, the run ends with `Success!`, and `echo` runs eleven
times. Here that is because `fail.cwl` computes its output with an
expression (`outputEval: $("not fail")`) rather than reading a file, so a
job that exited 1 still has an output. A tool whose output is a file it
failed to write ends with that output `null` instead, and that is where the
second half of the rewrite comes in.

## What the flag changes in the compiled CWL

Two things, both visible in the files of the tree in `autogenerated/`:

- Every tool gets `successCodes`, so that the exit codes you name count as
  success, and each of its outputs whose type is written as a string becomes
  optional: `string` becomes `string?`, `File[]` becomes `File[]?`, and a
  type already ending in `?` is left alone. An output whose type is written
  as a mapping (`{type: array, items: File}`) or a list is not changed, and
  stays required. A job that fails with one of those codes and leaves no
  output then ends with that output `null` rather than failing the step.
  `fail.cwl` compiled with the flag:

```yaml
outputs:
  failout:
    type: string?
    outputBinding:
      outputEval: $("not fail")
successCodes:
- 0
- 1
```

- Every step with required inputs gets a `when:` over them that runs it only
  when they are not `null`, replacing any `when:` it had. The compiled
  `echo` step:

```yaml
- id: echo
  in:
    message:
      source: fail/fail~failout
  run: test_rand_fail~echo.cwl
  out:
  - stdout
  scatter:
  - message
  when: $(inputs["message"] != null)
```

A step whose input came from a job that produced nothing is therefore
skipped, and its own outputs are `null` in turn, so the skip travels along
the arrows of the graph from the failed job, and no further. A step with several required inputs runs only when
all of them are present. A step with no required inputs keeps its own
`when:`, if it had one.

The codes that count as success are `0` plus those you name:

- `--partial_failure_success_codes 1 2` lists codes;
- `--partial_failure_success_codes_range 1 5` names a range, lower bound
  included and upper bound excluded.

Both default to `0` and `1`, so with the flag alone an exit status of `1` is
a partial failure and anything else still fails the step. Give a tool's real
failure codes; a code that means a crash should stay a failure.

## What to expect

- cwltool warns, for each step that reads from one with a `when:`, that the
  source `may produce null`. With the flag every step with required inputs
  has one, so the warning repeats; it is expected and changes nothing.
- A tool's own expressions are not rewritten. An `outputEval` that reads
  `self[0].contents` fails on a job that wrote nothing, even though the
  command's exit code was forgiven; write such expressions to return `null`
  when `self[0]` is missing, as the [developer guide](dev/devguide.md) shows.
- A plain CWL workflow under `--allow_raw_cwl` cannot take the flag, since
  Sophios compiles nothing to rewrite.
- `--cwl_inline_subworkflows` leaves a call nested when the flag added a
  `when:` to it.
- The flag is a command-line option. `Workflow.run()` has no partial-failure
  setting; write the workflow out with `write_wic()` and run it on the
  command line, giving any value bound on its inputs in an inputs file.

## What it is not

Partial failures do not retry a job, and do not make a workflow succeed that
produced nothing: a step with no surviving input is skipped, and a workflow
whose every job failed ends with empty outputs. The runner's output
(`output_<workflow>.json`) shows `null` where a job failed, which is how you
find out what was lost. For a tool that may legitimately fail and whose
failure a later step should see, give it a `successCodes` of its own and let
it write a marker output instead.

## Recap

`--partial_failure_enable` lets the exit codes you name count as success,
makes each tool's outputs optional, and gives every step with required
inputs a `when:` that skips it when an input is missing. The run goes on
past failed jobs, and `output_<workflow>.json` shows `null` where a job left
nothing.
