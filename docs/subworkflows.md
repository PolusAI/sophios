# Subworkflows

As a pipeline grows, parts of it start to have names of their own: "prepare
the sample", "fit the model". In this chapter you will take the part of the
greeting pipeline that makes the greeting, `touch` and `append`, and turn it
into a workflow of its own, then use that workflow as a single step of a
larger one. A workflow used as a step is a **subworkflow**. You can reuse it
in many workflows, and the steps around it connect to it as if its steps were
written in place.

In Python, the subworkflow is a `Workflow` object built by a function and
put in the parent's list of steps like any step. The parent reads its named

```{literalinclude} cookbook/nested.py
:language: python
:caption: nested.py
```

A step whose id ends in `.wic` runs that file, and Sophios finds it the way
it finds a tool: on a search path, this time `search_paths_wic` in
`~/wic/global_config.json`. Add your project directory to that list:

```json
"search_paths_wic": {"global": ["/home/you/wic/examples", "/home/you/sophios-tutorial"]}
```

Alternatively, `run: make_greeting.wic` on the step names the file by path,
relative to `nested.wic`, and needs no search path. Python looks nothing up.
Now run either form:

```bash
sophios --yaml nested.wic --run_local
```

```bash
python nested.py
```

Both succeed, and `cat` reads back `Hello`, the greeting the subworkflow
made. The Python run first reports the output you named in the child:

```text
Adding a new output greeting to workflow make_greeting
 starting compilation of nested
finishing compilation of nested
...
Success! Runner outputs are under /home/you/sophios-tutorial/autogenerated/outdir_cwltool_nested_2026_10_18_22.24.00/
```

### When to make a subworkflow

Make one when a part of a workflow has a name of its own and is worth
reusing: the same preparation in front of several analyses, or a piece a
colleague maintains. It costs a second file and an interface to keep in
step. A single step needs no subworkflow, since a tool is already reusable,
and a part used in one place only reads more easily where it is.

## What the subworkflow exposes

The child's `outputs:` say what it hands back by name. Every output of every
step inside it is kept too, under generated names, so nothing a step made
is lost. `output_nested.json` lists four outputs:

```text
cat~output
make_greeting~append~file
make_greeting~greeting
make_greeting~touch~file
```

`make_greeting~greeting` is the output you named, as the parent sees it.
`make_greeting~append~file` and `make_greeting~touch~file` are the
outputs of the child's own steps, their names joined to the step that
called the child, and `cat~output` is the parent's own last step.

A subworkflow takes values the same way a workflow does: declare them under
`inputs:` in the child, and give them values on the calling step's `in:`, by
name. In Python, the function that builds the child is the interface: give
it parameters for its inputs, and set `child.outputs.<name>` for its
outputs, as `make_greeting()` does.

## Connections across the boundary

Connections and edge inference see through the call. A step after the call
may be connected to an output of a step inside the child, and a step inside
the child to an output of a step before the call. A note about such a choice
names the inner step by the path to it, as in
`make_greeting.wic > append`'s file, and you pin it in the child's file. Splitting a workflow into subworkflows changes the
names in the compiled CWL and nothing else: the same steps, connections and
values. [Drawing a workflow](drawing.md) draws each subworkflow as a box
around its steps, which is a quick way to check the connections across it.

A calling step takes the keys any step takes, so `scatter:` on a call runs
the whole subworkflow once per element, over the inputs the child declares,
and `when:` decides whether it runs at all.

## When it goes wrong

A subworkflow found neither on `search_paths_wic` nor at its `run:` path is
`wic013` at the calling step, and so are subworkflows that call each other
in a circle. Scattering a call over a name the child does not declare is
`wic032`. In Python, two children of one workflow may not share a name
(`api002`). On a search path, a `.wic` file whose path contains `_inputs`
is skipped, so an inputs file left beside your workflows is never read as
one.

A caller can also set values on the steps inside a child without editing the
child's file, through the `wic:` block of the `.wic` file;
[§7 of the `.wic` reference](wic-reference.md#7-the-wic-block) describes it.
In Python, pass the value as a parameter of the function that builds the
child.

## Recap

A subworkflow is a workflow used as a step: a `.wic` file named by a step's
id or `run:`, or a `Workflow` object in a Python list of steps. Its
`outputs:` name what it hands back, every inner output is still kept, and
connections and inference cross the boundary as if the steps were written in
place.
