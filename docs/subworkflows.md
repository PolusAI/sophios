# Subworkflows

How do I split a workflow into named parts, reuse a part in several workflows,
and give a part an interface? A subworkflow is a workflow used as a step. In
`.wic` it is another `.wic` file; in Python it is a `Workflow` object in the
parent's step list. Inference and edges work across the boundary as if the
steps were written in place, which is what makes splitting safe.

In `.wic`, a step whose id ends in `.wic` runs that file, found on
`search_paths_wic` of the [configuration](configuration.md): to run
`nested.wic` from your working directory, that directory must be listed there,
as [Install](install.md) sets up. `run: child.wic` names a file by path,
relative to the document, instead. In Python, a `Workflow` in a parent's step
list is the subworkflow, and the parent reads its named outputs like a
step's; nothing is looked up. The parent calls the child as one step, and the
child keeps its own identity in the compiled result
([Compiling to CWL](compiling-to-cwl.md#subworkflows)). `.wic` search paths
follow the same rules as tool search paths: recursive, a repeated stem warns
and the later file wins, and nothing under `autogenerated/` is found. A file
whose path contains `_inputs` is skipped, so a job file left in a workflow
directory is not read as a workflow.

## The interface

A subworkflow's `inputs:` says what its caller gives it, and its `outputs:`
what it exposes by name:

```yaml
# child.wic
inputs:
  filename: string
steps:
  touch:
    in:
      filename: filename
```

```yaml
# the caller
steps:
- id: child
  run: child.wic
  in:
    filename: !ii data.txt
```

The caller binds a declared input like any step input, by name. A value the
subworkflow expects from outside is declared this way; `!*` asks the whole
compilation for an edge instead, and a reference that nothing defines is
`wic025` at the root. In Python the interface is the function that builds the
child: its parameters are the inputs, and `child.outputs.<name> = ...` the
outputs, as `make_greeting()` shows.

Beyond the named outputs, every output of every inner step is exposed by the
child and again by the parent, under generated names
(`make_greeting__touch__file`),
so that nothing a step produced is lost. In Python, a parent that names its
own outputs returns only those from `compile()`; see
[Connecting steps](connecting-steps.md).

A subworkflow call takes the keys a step takes. `scatter:` over a call
scatters the inputs the child declares, and only those; `when:` on a call
reads them. A call with `scatter`, `when` or any key besides `in` and `out`
is never flattened by `--cwl_inline_subworkflows`.

## Inference across the boundary

Inference sees through the call. A step after the call may be connected to an
output of a step inside the child; a step inside the child may be connected to
an output of a step before the call. The note that reports a choice names an
inner port by the path of steps down to it, and the pin goes on that inner
step, in the child's file. Explicit edges cross the boundary the same way: an
edge defined in the caller before the call may be used inside the child, and
an edge defined inside the child may be used after the call. The one
exception is a record with several sources, which takes each from its own
document.

Splitting a workflow into subworkflows therefore changes the names in the
compiled CWL and nothing else: the same steps, the same edges, the same job
inputs. [Drawing](drawing.md) shows a subworkflow as a cluster, which is the
quickest way to confirm that the edges you expected were inferred across it.

## In `.wic` only: settings from the caller

A caller may set inputs, outputs and inference rules on the steps inside the
subworkflow it calls, without editing the child's file, through the `wic:`
block:

```yaml
steps:
- id: child
  run: child.wic
wic:
  steps:
    (1, child):
      wic:
        steps:
          (1, touch):
            in:
              filename: !ii other.txt
```

The keys are `(index, name)`, the 1-based position and id of the step
addressed, or the bare id of a step that occurs once; a key addressing no step
prints a line on stderr naming the step at that position, and is ignored. The
[`.wic` reference](wic-reference.md) lists everything the `wic:` block
takes, including `inlineable: false`, which keeps a subworkflow nested under
`--cwl_inline_subworkflows`. A Python workflow has no `wic:` block: pass the
value as a parameter of the function that builds the child.

## What can go wrong

- A subworkflow not found on `search_paths_wic` or at its `run:` path is
  `wic013`, at the calling step. A root workflow with no steps is an error
  too, with no position.
- Subworkflows that call each other in a cycle are `wic013`.
- A child whose `inputs:` or `outputs:` are written as a list holding an
  `$import` or `$include` is `wic013`: no caller can be checked against ports
  only the CWL runner can read.
- Scattering a call over a name that is not one of the child's declared
  inputs is `wic032`.
- In Python, two children of one workflow, steps or nested workflows, may not
  share a name (`api002`); and two steps anywhere in the tree whose tools
  share a file stem but differ in content are `api002` too, since a document
  names a tool by its stem.

## Flattening

`--cwl_inline_subworkflows` writes one flat workflow instead of a tree: each
call that carries nothing but `in` and `out`, and whose child is not marked
`wic: inlineable: false`, is replaced by the child's steps, renamed for where
they came from; the tools stay separate files. Each call that stays nested is
named on stderr with the reason. `--cwl_inline_runtag` is the other packaging
option, one self-contained file with every process embedded under `run:`;
[Compiling to CWL](compiling-to-cwl.md) shows both. Neither changes what the
workflow does.
