# Cookbook

One short example per construct of the language, written twice: as a `.wic`
document and with the Python API. The two spellings of each example compile to
the same CWL and the same job inputs; `tests/core/test_cookbook.py` compiles
every pair both ways and fails if they differ. The [Language Guide](language_guide.md)
explains each construct in full, and the [Python Workflow API](userguide.md)
guide covers the Python side.

The files are in `docs/cookbook/` of the Sophios repository. Each example uses
tools from `cwl_adapters/`, and each Python script finds them relative to its
own file. Compile a `.wic` example from the repository root, with `cwl_adapters`
on `search_paths_cwl` in your configuration file:

```bash
sophios --yaml docs/cookbook/explicit_edge.wic --generate_cwl_workflow
```

This writes `autogenerated/explicit_edge.cwl` and the job inputs,
`autogenerated/explicit_edge_inputs.yml`. Compile a Python example by calling
its `workflow()`:

```python
from pathlib import Path

from sophios.python_cwl_adapter import import_python_file

module = import_python_file('explicit_edge', Path('docs/cookbook/explicit_edge.py'))
compiled = module.workflow().compile()
print(compiled.to_cwl_yaml())
print(compiled.to_job_inputs_yaml())
```

Three things about the compiled CWL hold for every example below:

- Each step is renamed `<workflow>__step__<n>__<id>`, where `n` is its position.
- A literal value is not written into the CWL. It becomes a workflow input named
  `<renamed step>___<port>`, and its value goes in the job inputs.
- Every step output is also a workflow output, named `<renamed step>___<port>`,
  unless the Python workflow passed to `compile()` names its outputs (see
  [A named workflow output](#a-named-workflow-output)). Named outputs on a
  nested workflow do not change this: its step outputs are still exposed, by
  it and by its parent.

The excerpts show only the lines each construct changes.

## An inline literal

```{literalinclude} cookbook/inline_literal.wic
:language: yaml
```

```{literalinclude} cookbook/inline_literal.py
:language: python
```

`!ii` in a `.wic`, and a plain Python value, bind the input to that value.
The value goes in the job inputs:

```yaml
# inline_literal.cwl
steps:
- id: inline_literal__step__1__touch
  in:
    filename:
      source: inline_literal__step__1__touch___filename
# inline_literal_inputs.yml
inline_literal__step__1__touch___filename: empty.txt
```

## A workflow input

```{literalinclude} cookbook/workflow_input.wic
:language: yaml
```

```{literalinclude} cookbook/workflow_input.py
:language: python
```

An untagged name in a `.wic`, and `flow.inputs.<name>` in Python, binds the input
to a workflow input that is given when the workflow runs. Python declares the
workflow input from the first binding, with the type of the port it feeds:

```yaml
inputs:
  filename:
    type: string
steps:
- id: workflow_input__step__1__touch
  in:
    filename: filename
```

## An explicit edge

```{literalinclude} cookbook/explicit_edge.wic
:language: yaml
```

```{literalinclude} cookbook/explicit_edge.py
:language: python
```

`!&` names a step output and `!*` uses it; in Python, binding a step output to a
later step's input is the edge. The edge becomes a `source`:

```yaml
- id: explicit_edge__step__2__append
  in:
    file:
      source: explicit_edge__step__1__touch/file
```

## A raw CWL reference

```{literalinclude} cookbook/raw_cwl.wic
:language: yaml
```

```{literalinclude} cookbook/raw_cwl.py
:language: python
```

`!cwl` on a string writes it into the CWL as it is, without checking it. Python
has no unchecked spelling: a reference is always a port object, so the Python
twin of `!cwl greeting`, which names a workflow input, is that workflow input.
Both write the same line:

```yaml
- id: raw_cwl__step__1__echo
  in:
    message: greeting
```

## A step-input record

```{literalinclude} cookbook/record.wic
:language: yaml
```

```{literalinclude} cookbook/record.py
:language: python
```

`!cwl {...}` in a `.wic`, and `StepInput` in Python, write CWL's step input, here
two sources merged into one `File[]`. The `.wic` gives the `concat` tool inline
under `run:`; Python builds the step from the same document with
`Step.from_cwl_document`. Sophios adds `MultipleInputFeatureRequirement`:

```yaml
requirements:
  MultipleInputFeatureRequirement: {}
steps:
- id: record__step__3__concat
  in:
    files:
      source:
      - record__step__1__touch/file
      - record__step__2__echo/stdout
      linkMerge: merge_flattened
```

## Scatter

```{literalinclude} cookbook/scatter.wic
:language: yaml
```

```{literalinclude} cookbook/scatter.py
:language: python
```

`scatter:` and `scatterMethod:` in a `.wic`, and `scatter_on(..., method=...)` in
Python, run the step once per combination of the scattered arrays; the output is
an array. Sophios adds `ScatterFeatureRequirement`:

```yaml
requirements:
  ScatterFeatureRequirement: {}
steps:
- id: scatter__step__1__echo_3
  scatter:
  - message1
  - message2
  scatterMethod: flat_crossproduct
outputs:
  scatter__step__1__echo_3___stdout:
    type:
      type: array
      items: File
```

## A conditional step

```{literalinclude} cookbook/when.wic
:language: yaml
```

```{literalinclude} cookbook/when.py
:language: python
```

`when:` in a `.wic`, and `step.when` in Python, run the step only when the
expression is true. The expression reads `enabled`, which `echo.cwl` does not
take, so a record binds it to the workflow input `loud`. A record that feeds an
input the tool does not declare gives the workflow input no type, so the `.wic`
declares `loud` under `inputs:`, and Python declares it with
`.as_type('boolean')`.
Sophios adds `InlineJavascriptRequirement`:

```yaml
inputs:
  loud:
    type: boolean
steps:
- id: when__step__1__echo
  in:
    enabled:
      source: loud
  when: $(inputs.enabled)
```

## A nested workflow

```{literalinclude} cookbook/nested.wic
:language: yaml
```

```{literalinclude} cookbook/make_greeting.wic
:language: yaml
:caption: make_greeting.wic
```

```{literalinclude} cookbook/nested.py
:language: python
```

A step named for a `.wic` file, and a `Workflow` in a workflow's step list, run
that workflow as one step, and a later step reads one of its named outputs. The
step `make_greeting.wic` is found by its file stem, so put `docs/cookbook` on
`search_paths_wic` to compile `nested.wic` with `sophios --yaml`. Sophios adds
`SubworkflowFeatureRequirement`:

```yaml
requirements:
  SubworkflowFeatureRequirement: {}
steps:
- id: nested__step__2__cat
  in:
    file:
      source: nested__step__1__make_greeting.wic/greeting
```

## Inference

```{literalinclude} cookbook/inference.wic
:language: yaml
```

```{literalinclude} cookbook/inference.py
:language: python
```

An input that nothing binds, here `cat`'s `file`, is connected by inference to
the most recent earlier output of a matching type. Two earlier outputs match, so
the compile takes `echo`'s and says so in a note. `sophios --yaml` prints it on
stderr; in Python it is in `compiled.diagnostics`, positioned at the Python line
that made the step (`cat = Step(...)`):

```text
inference.wic:8:3: note [wic043] step 'cat' input 'file' was inferred from the most recent match 'echo/stdout'; earlier steps also match: 'touch/file'; pin it: `out: - stdout: !& <name>` on step 'echo' and `in: file: !* <name>` here (step 3 'cat', port 'file')
```

```yaml
- id: inference__step__3__cat
  in:
    file: inference__step__2__echo/stdout
```

To choose the other output, or to keep this one without the note, bind the input
explicitly, as in [An explicit edge](#an-explicit-edge).

## A named workflow output

```{literalinclude} cookbook/named_output.wic
:language: yaml
```

```{literalinclude} cookbook/named_output.py
:language: python
```

`outputs:` with `outputSource: <step>/<output>` in a `.wic`, and
`flow.outputs.<name> = step.outputs.<output>` in Python, expose a step output
under a name you choose:

```yaml
outputs:
  greeting:
    type: File
    outputSource: named_output__step__1__echo/stdout
```

This is the one place the two spellings give different CWL. When a Python
workflow names outputs, `compile()` returns only those. `sophios --yaml` also
keeps every step output as a workflow output, as it does in the other examples:

```yaml
  named_output__step__1__echo___stdout:
    type: File
    outputSource: named_output__step__1__echo/stdout
```

## A renamed step

```{literalinclude} cookbook/renamed_step.wic
:language: yaml
```

```{literalinclude} cookbook/renamed_step.py
:language: python
```

`id:` with `run:` in a `.wic`, and `step_name=` in Python, give a step a name of
its own, here so that one tool runs twice in one workflow. `run: echo` names the
tool by its file stem. The step names reach the CWL:

```yaml
steps:
- id: renamed_step__step__1__hello
- id: renamed_step__step__2__goodbye
```
