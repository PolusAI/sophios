# Nextflow DSL2 target

Sophios can compile supported workflows to a validated Nextflow intermediate
representation and deterministic DSL2 artifacts. CWL remains the canonical
compiler representation; the Nextflow target converts the compiler's
already-inferred workflow graph without running inference a second time.

The target fails closed: a CWL field, type, requirement or hint it does not
consume is rejected by name, before any artifact is written, never dropped.
[Field support](#field-support) lists what it does with each one.
`target="nextflow"` accepts no user-written Groovy; every string you write is
rendered as data.

## Python API

```python
from sophios.api.python.workflow import Workflow

workflow: Workflow = build_workflow()
nextflow_ir = workflow.compile(target="nextflow")
json_path, script, config, params = workflow.to_nextflow("autogenerated")
```

Calling `workflow.compile()` or `workflow.compile(target="cwl")` continues to
return `CompiledWorkflow`. The Nextflow target returns
`ExecutableNextflowWorkflow`, a closed, immutable representation with typed
command tokens, ports, resources, and connections. Its versioned JSON form,
`nextflow_workflow.json`, is a record of it that nothing reads back.

## Command line

```console
sophios --yaml workflow.wic --target nextflow
```

The command writes four files under the base path, `autogenerated/` unless
`--basepath` names another directory:

- `nextflow_workflow.json`
- `workflow.nf`
- `nextflow.config`
- `nextflow_params.json`

A rejected workflow leaves none of them behind, including any an earlier run
wrote there; `workflow.to_nextflow(outdir)` does the same in `outdir`.

Run the result with a compatible Nextflow installation:

```console
nextflow run autogenerated/workflow.nf \
  -params-file autogenerated/nextflow_params.json \
  -c autogenerated/nextflow.config
```

or let Sophios run it, as [Running on the Nextflow target](#running-on-the-nextflow-target)
describes.

The pipeline checks every workflow input value against its declared type
when it starts, before any task runs. A value given on the command line, as
`--name value`, is text, and so is a JSON string in the params file. Text
converts only when it is exact: `true` or `false` for a `boolean`, a whole
number within the 32-bit range for an `int`, and a finite decimal number for
a `float`; a number given for a `float` must be finite too, and
[Floats](#floats) says how the params file carries one. A `File` or
`Directory` value is a path, or a CWL File or Directory object with a `path`
and, if it has a `class`, the declared one, and must name an existing file or
directory of that kind; a relative path is relative to the directory Nextflow
is launched from. A path that names nothing of that kind stops the run with
`Sophios workflow input '<name>' must be <type>; no <kind> exists at
'<path>'`. An array comes only from the params file, and `[]`
stands for an absent optional value that is not a `File` or `Directory`; an
absent optional `File` or `Directory` workflow input is rejected when the
workflow compiles. Any other value stops the run with `Sophios workflow input
'<name>' must be <type>, not <value>`, where `<name>` is the parameter as the
params file spells it.

The pipeline needs Nextflow's v2 script parser, its default. Under
`NXF_SYNTAX_PARSER=v1` Nextflow converts a command-line value itself, so
`--name 010` arrives as the number 10, and the pipeline stops before any task
with `Sophios-generated Nextflow needs the v2 script parser: unset
NXF_SYNTAX_PARSER or set it to v2`.

Sophios does not support dry runs. Every generated process has a `stub:`
block that prints `Sophios-generated Nextflow does not support dry runs
(-stub-run)` and exits 1, so `-stub-run` stops at the first task and runs no
command.

When a workflow output completes, the pipeline prints it on one line of
standard output: `sophios-output`, then the JSON array of the output's name
and its value. A file or directory is an object with its `class` and its
absolute `path`, in Nextflow's work directory; a captured text is a string;
a null is `null`; and the output of a scattered step is an array, one level
deep for each input a `nested_crossproduct` scatters. A
[Sophios run](#running-on-the-nextflow-target) reads these lines back as the
workflow's output object.

`sophios --help` groups the options by target. An option of another target,
set away from its default, is an error: `--target nextflow` cannot be combined
with a CWL-only option such as `--generate_cwl_workflow`, `--inputs_file`,
`--outdir`, `--cachedir`, `--quiet`, `--container_engine`, `--graphviz` or
`--partial_failure_enable`. `--run_local`, `--generate_run_script`, `--check`
and `--passthrough_flags` act under both targets.

### Floats

A float reaches the command as Python's `str()` writes it: the shortest
digits that read back as the same value, such as `0.1`, `5.0`, `0.0001`,
`1e-07`, `1e+16` and `-0.0`. A whole number given for a `float`, a default
included, is that float, so `5` reaches the command as `5.0`. Sophios writes
each float into `nextflow_params.json` as text, such as `"-0.0"`, because
Nextflow reads a JSON number with a point or an exponent without the sign of
a zero. A JSON number you write into the params file for a `float` works too,
as Nextflow reads it: a whole number keeps its integer text, such as
`3000000000`, and `0.0` is `0.0`, but `-0.0` written as a number reaches the
command as `0.0`, and a whole number past the 64-bit range has wrapped before
the pipeline sees it. Write such a number as text, such as `"-0.0"`, to keep
it exact.

The CWL target prints a float differently, and the Nextflow target does not
follow it, since cwltool changes some values. cwltool writes a float from the
job file or a tool default as the file spells it, `1.50` as `1.50`, and
rounds one spelled with an exponent to a whole number, so `1e-07` reaches the
command as `0` and `1e+16` as `10000000000000000`; only a float inside a
longer string, such as `x=$(inputs.x)`, reaches it as Python's `str()`. The
two targets print the same text for a float Sophios writes that is zero or
from `0.0001` up to, but not including, `1e16` in size, except a whole-number
default, which cwltool prints as spelled, `5`, and the Nextflow target as the
float, `5.0`.

## Running on the Nextflow target

Sophios runs the pipeline as it runs a CWL workflow, as one `nextflow run`
on this machine:

```console
sophios --yaml workflow.wic --target nextflow --run_local
```

```python
result = workflow.run(target="nextflow")
print(result.outputs)
```

`Workflow.start(target="nextflow")` and `Workflow.run_async(target="nextflow")`
follow the run as they follow a CWL one ([Running](running.md#follow-a-run-from-python)).
`--generate_run_script` writes the command to `run.sh` instead, and `--check`
writes the four files and checks the machine: that each input file or
directory can be read (`wic016`), that `nextflow` starts, which needs a Java
it can run (`wic029` when it does not), and, when a process has a container,
that Docker can run it (`wic015`). `run.sh` calls the `nextflow` on PATH, so
`--generate_run_script` looks for it there. On Windows Sophios runs Nextflow
inside WSL only. The pipeline also checks its input values itself when it
starts.

From Python, a workflow that declares outputs is lowered with only those,
as `compile()`, `compile(target="nextflow")` and `to_nextflow()` lower it,
so its run reports the outputs a CWL run of it reports.

Before the run Sophios writes the four files to `nextflow_<workflow>/` in
the base path from the workflow's values, with each relative path made
absolute: read beside the `.wic` file on the command line, from the working
directory in Python. It makes each output directory a tool writes into
([Staging with InitialWorkDirRequirement](#staging-with-initialworkdirrequirement))
that does not exist yet, and writes `nextflow_names.json` beside the four
files, the Sophios name of each process and workflow output by its Nextflow
name. The directory is named after the workflow, as a CWL run's files are,
so runs of two workflows started together from one base path keep apart. It
then starts

```console
nextflow -C <dir>/nextflow.config run <dir>/workflow.nf \
  -params-file <dir>/nextflow_params.json -work-dir <dir>/work -ansi-log false
```

from that directory, `<dir>`, so the work directory, `.nextflow.log` and
`.nextflow/` are there with the pipeline they belong to. `-C` makes
`nextflow.config` the only configuration Nextflow reads: a `nextflow.config`
in the working directory or `~/.nextflow/config` takes no part.

When the run succeeds, its outputs are the workflow's output object, from
the lines the pipeline prints: each output by its Sophios name, a file or
directory as a CWL object with its `class`, `location`, `path` and
`basename`. The object is also written to `output_<workflow>.json` in the
base path, as for a CWL run. The files are where Nextflow made them, in the
work directory, and nothing copies them elsewhere. When the run fails, each
process Nextflow names as failing is reported by its step name with its exit
status. A [real-time analysis](realtime-analysis.md) does not run beside
Nextflow, and a line on stderr says so.

Every option of `nextflow run`, an executor among them, is yours to pass,
unchecked, as a CWL runner's options are. On the command line add
`--passthrough_flags yes` and the options; they follow the command above. In
Python each `run_args_dict` key Sophios does not read becomes
`-<key> <value>`, or `-<key>` alone for an empty value, since Nextflow's
options take one dash, and a key only a CWL run reads is a `ValueError`. An
option of the `nextflow` launcher itself, such as `-log`, `-q` or `-D`,
belongs before `run`, so it cannot be passed:

```console
sophios --yaml workflow.wic --target nextflow --run_local --passthrough_flags yes -process.executor slurm -resume
```

```python
workflow.run(target="nextflow", run_args_dict={"process.executor": "slurm", "resume": ""})
```

Sophios does not check what an executor does with the tasks; that is the
executor's contract. A run started from `nextflow_<workflow>/` in the base
path reads a relative path you pass from there. Passing a configuration file
or `-stub-run` this way is not supported: Sophios supports neither
user-written configuration nor dry runs. `run.sh` holds the same command, and
runs it from wherever you start it.

## Names

Process and parameter names come from the step ids of the compiled CWL. A
step id is as written, and a repeated id carries `@<position>`. A name
Sophios makes joins the step and the port with `~`, as `touch~filename`, and
a step in a nested workflow is named through the step that calls it, as
`child~inner_copy`. Characters Nextflow does not allow in a name become `_`,
so these become the parameter `touch_filename` and the process
`child_inner_copy`. A name Nextflow would read as something else gains a
leading `_`: a reserved word, a name that starts with a capital letter (Groovy
reads it as a class), `task`, `log` and `channel`, and, for a process or the
workflow, a name every Nextflow script declares, such as `file`, `params` or
`main`. A workflow named like one of its steps gains a leading `_` as well.
Two names that become the same are rejected, and the message names both as
written.

## Importing supported DSL2

```python
from sophios.api.python.nextflow import import_nextflow

workflow = import_nextflow("autogenerated")
nextflow_ir = workflow.compile(target="nextflow")  # the model the pipeline was written from
workflow.write_wic("imported")                     # the workflow as .wic
workflow.compile().write_job_inputs("imported")    # and its values, as a CWL job
```

`import_nextflow(directory)` reads a pipeline Sophios wrote, from the three
files Nextflow itself reads: `workflow.nf`, `nextflow_params.json`, which
holds the job values, and `nextflow.config`. It does not read
`nextflow_workflow.json`, which records the model for you and which nothing
reads back, and it reads no tool registry, no network and no path a
parameter names. It builds one Sophios `Workflow` through the Python API: a
`CommandLineTool` made a step for each process, in the order the pipeline
calls them; each parameter a workflow input holding its value; and every
edge bound on the input it feeds, so the workflow leans on no inference.
Compiled to Nextflow, the workflow gives back the model the files were
written from, and so the same files. A value bound on a workflow input is
that input's value in the job either target compiles; `write_wic` leaves the
input open, so the values are in the job alone.

The supported DSL2 is what Sophios writes, and the only freedom is layout:
indentation, the length of a run of spaces or tabs, blank lines, line and
block comments, the order of the process blocks, and CR LF line endings, but
not inside a string, a script or stub, or a generated helper, which must be
as Sophios wrote them; in `nextflow_params.json`, JSON's own whitespace and
key order. A line break, and the order of the statements in `main:`, are not
layout. Anything else stops the import with a diagnostic at its line
([error codes](error_codes.md)), and nothing is returned:

- an edited helper, `wic047`;
- a statement, directive or channel operator Sophios does not write, such as
  an `include`, an `errorStrategy` or a `.view()`, `wic048`;
- an input or output declaration Sophios does not write, such as
  `tuple val(id), path(reads)`, `wic049`;
- a script that is not the generated command, or an edited stub, `wic050`;
- a params file that does not hold one value, in the form Sophios writes,
  for each parameter the pipeline checks, `wic051`;
- a `nextflow.config` other than the generated one, `wic052`;
- text in the generated forms that is not what Sophios writes for the
  workflow the text describes, such as a derived form that disagrees with the
  rest, `wic053`;
- a pipeline no workflow built through the Python API compiles to as it is
  written, `wic054`: a name the compile would change, such as a capitalized
  process name, which it writes with a leading `_` (see [Names](#names)), or
  a port of a CWL tool named like an attribute of the tool builder's `Inputs`
  or `Outputs`, such as `keys`. Rename it in the workflow the pipeline came
  from, and compile it again.

The import is exact on the model, not on the Sophios workflow the model came
from. What the compile does not keep does not come back:

- original names: the import keeps the Nextflow spellings, so a value written
  on a step is a workflow input named `<step>_<port>`, and a name that gained
  a leading `_` keeps it; normalization is idempotent, so a second round trip
  is exact;
- nesting: subworkflows are inlined, so the workflow is flat;
- labels, docs, the other compile-time fields of [Field support](#field-support),
  and Sophios-only hints;
- `cudaDeviceCountMax`: the `accelerator` count is read as
  `cudaDeviceCountMin`, the count both runners ask for;
- comments and formatting;
- every choice that lowers to the same model: where a value came from (a
  tool's default, a step's default, an unbound optional input and a value
  written on a step each become a workflow input holding it); a maximum
  resource, read as the count it lowered to; `dockerImageId`, read as
  `dockerPull`; whether a requirement was a hint; `$(inputs.<name>.path)`,
  read as `$(inputs.<name>)`; `type: stdout`, read as a `File` output that
  globs the `stdout` name; whether a token came from an argument or an
  input's own binding, and its position; a single-input scatter's method;
  the spelling of a `when`; adjacent `shellQuote: false` texts, read as one;
  and a tool's input order.

Two facts the workflow needs and that nothing in the rest of the text gives
ride in each process's `ext` directive, which no generated script reads: a
`cwltool:CUDARequirement`'s `cudaVersionMin` and `cudaComputeCapability`
([GPUs](#gpus)), and which outputs are a `Directory`
([Output cardinality](#output-cardinality)).

## Boolean flags

A `boolean` input with an `inputBinding` prefix becomes a real command-line
flag: `true` contributes the prefix as exactly one argument and `false`
contributes nothing. A boolean binding without a prefix contributes nothing
for either value, matching CWL. An absent optional boolean now renders
identically to `false`, since a flag never dereferences its value.

A `valueFrom` on a boolean binding is supported only as a bare
`$(inputs.<name>)` reference restating the binding's own input — a redundant
but legal CWL form that lowers to the same flag. Any other `valueFrom` shape
on a boolean binding is rejected.

The same rule applies wherever a `valueFrom` is exactly `$(inputs.<name>)` of a
boolean input — an `arguments` entry or another input's binding: the flag uses
that entry's prefix. On an optional input's binding it is rejected, since CWL
omits the whole binding when that input is absent.

## Absent optional values

An absent optional `val` input (string/int/float/boolean) lowers to a
reserved `[]` sentinel parameter when its consuming tool input is never
dereferenced in that tool's command, stream targets, or output globs, or is
referenced only by the boolean flag it drives or by its own binding. `[]` is
used instead of `null` because `Channel.value(null)` never binds under the
pinned Nextflow runtime and the run hangs; `[]` is Groovy-falsy like `null`,
so flag rendering is unaffected.

An optional `string`, `int` or `float` input's own `inputBinding`, with no
`valueFrom`, adds nothing for `[]`, prefix included, as CWL adds nothing for
a null input; any other value adds the prefix and the value as the binding of
a required input does. Any other reference to an absent input, a `valueFrom`
on its own binding included, and any absent optional `File`/`Directory` or
array input, is rejected.

## Basename references

`$(inputs.<name>.basename)` is supported in command arguments, stream targets,
and output globs, so a tool can name its outputs after a staged input:

```yaml
outputs:
  result:
    type: File
    outputBinding:
      glob: $(inputs.source.basename).copy
```

The reference must target a `File` or `Directory` input. Nextflow stages an
input under its original file name, so the staged name is exactly the CWL
`basename`. `$(inputs.<name>.path)` is the same reference as `$(inputs.<name>)`
and is likewise admitted only on a `File` or `Directory` input. A bare
`$(inputs.<name>)` of a `File` or `Directory` input must be the whole value:
embedded in other text, such as `--input=$(inputs.f)`, CWL renders the File
object as JSON, so it is rejected; write `$(inputs.f.path)` there instead.

A string holding a `$(…)` reference is interpolated as cwltool does: it is
stripped of surrounding whitespace, `\$(` writes a literal `$(`, and `\\`
writes one backslash. A string with no reference is used exactly as written.
A `$` that is not followed by `(` or `{` is plain text, so a literal argument
such as `mv a "$1"` reaches the command as written.

The `.copy` suffix above is load-bearing: a basename glob must derive a **new**
name. A glob that is only a reference to a `File` or `Directory` input names
the staged input, which a CWL glob does not match, so it is rejected. The
exception is an input made an `InitialWorkDirRequirement` entry under its own
name, below: the glob then names the entry.

A glob built only from basename references is matched literally, so a staged
name containing `*`, `?`, `[`, `{` or `}` still finds the file. A `*`, `?` or
`[` written into the literal part of a glob stays a pattern; a brace is matched
literally, since a CWL glob has no brace expansion.

## Array-typed inputs

```yaml
inputs:
  names:
    type:
      type: array
      items: string
    inputBinding:
      prefix: --name
```

An array input of `File`, `Directory`, `string`, `int`, `float`, or `boolean`
items is supported. It carries the same qualifier its item type would carry
alone (`path` for File/Directory, `val` for scalars); a `path` array stages
every element for one process call rather than fanning the channel out, and
renders as `path <name>, arity: '0..*'` so the process always receives a list,
whether the array holds no file, one, or many. Each file is staged in its own
numbered directory, so same-named files from different directories never
collide. The one supported command-line
binding shape (no `itemSeparator`) contributes its optional prefix once,
followed by each element as its own argument, and contributes nothing at all
when the array is empty. An empty array is a present, valid value — distinct
from an absent optional value above.

`itemSeparator`, `separate: false`, and `valueFrom` on an array binding are
not supported, nor are the shorthand `File[]` type form, nested arrays, a
per-item `inputBinding`, or array-typed outputs. A binding on a `boolean`
array is rejected: CWL adds only its prefix, when the array is not empty, and
never an item's `true` or `false`.

## Shell mode

`ShellCommandRequirement` alone changes nothing: every command token is
already individually shell-quoted and joined into one line, matching CWL's
own shell-mode quoting. `shellQuote: false` opts one binding out of quoting
so it can carry real shell syntax — pipes, redirections, globs — and is
supported only for a prefix-free binding whose `valueFrom` is a CWL-author
literal with no input reference at all:

```yaml
requirements:
  ShellCommandRequirement: {}
arguments:
- printf
- "%s"
- $(inputs.message)
- valueFrom: ">>"
  shellQuote: false
- out.txt
```

`shellQuote: false` on a binding with no `valueFrom`, with a `prefix`, or
whose `valueFrom` references any input — directly, or via a `.path`/
`.basename` suffix — is rejected: unquoting a runtime-supplied value would
let workflow input data or a chosen file name be interpreted as shell
syntax, which is exactly the boundary this lowering must not cross. A `$` in
the literal is rejected too: the task's shell would expand it in its own
environment, not CWL's.

## Environment variables

`EnvVarRequirement` sets variables for the command, in list or map form:

```yaml
requirements:
  EnvVarRequirement:
    envDef:
      RDKIT_ERROR_LOGGING: $(inputs.rdkit_error_logging)
      CONDA_PREFIX: /opt/conda/
```

A value is literal text, or exactly `$(inputs.<name>)` of a `string` input.
The task exports each variable, its value shell-quoted, before the command
runs, so the command sees the value byte for byte. In literal text a `$` that
is not followed by `(` or `{` is plain text. A referenced optional input
needs a value. Any other value is rejected by name: a reference to an input
of another type, `.path` or `.basename`, a reference inside other text, or any
other expression. So is a name that is not a shell variable name.

## Containers

A tool's `DockerRequirement` image becomes its process's `container`
directive, and a tool without one runs on the host; one workflow may hold
both. `nextflow.config` enables Docker when any process has a container.

CWL gives the command to the container as its arguments, so the image's
`ENTRYPOINT` runs first, and a tool with no `baseCommand` relies on it.
Each containerized process clears the entrypoint and runs its command after
the entrypoint's words: its `beforeScript`, on the host where the task
starts, pulls the image if it is missing and writes its `ENTRYPOINT` to a
hidden file in the task directory, which the script reads. The host needs
the `docker` command, as Nextflow's own Docker support does. A tool with
both `DockerRequirement` and `ShellCommandRequirement` is rejected: CWL runs
its command as `/bin/sh -c` after the entrypoint. So is a containerized tool
whose command can render empty, with no `baseCommand`, no `arguments` and no
bound input but optional, boolean or array ones: CWL then gives its container
no arguments, so the image runs its `CMD`; name the program in `baseCommand`.

## GPUs

`cwltool:CUDARequirement`, as a requirement or a hint, becomes the
`accelerator` directive. The count is `cudaDeviceCountMin`, else
`cudaDeviceCountMax`, else 1, the count cwltool asks for. A count is a whole
number; an expression is rejected. `cudaVersionMin` and
`cudaComputeCapability` have no Nextflow counterpart: the process carries
each one present, as written, in its `ext` directive, which no generated
script reads. The generated pipeline does not check them, and compiling
reports each one with the note [`wic046`](error_codes.md). The command line prints the note with the other
diagnostics; the Python API gives it as a `UserWarning`. Where a task runs is
the executor's choice: the local executor accepts the directive and runs the
task on the machine as it is.

## Staging with InitialWorkDirRequirement

A `listing` entry names one `File` or `Directory` input: the bare
`$(inputs.<name>)` shorthand, or a `Dirent` whose `entry` is that reference.
The entry keeps the input's own name when `entryname` is absent or
`$(inputs.<name>.basename)`, and takes a literal `entryname` otherwise.
Nextflow stages the input in a hidden directory, and the task makes the entry
before the command runs: a copy when `writable: true`, so the command may
change it without touching the input, and a symlink otherwise. Because the
task makes the entry, an output glob matches it as a CWL glob does.

An entry under the input's own name is what the input names: a reference to
the input, plain, `.path` or `.basename`, names the entry. This is how a tool
writes into an output directory it is given:

```yaml
requirements:
  InitialWorkDirRequirement:
    listing:
    - entry: $(inputs.outDir)
      writable: true
inputs:
  outDir:
    type: Directory
    inputBinding:
      prefix: --outDir
outputs:
  outDir:
    type: Directory
    outputBinding:
      glob: $(inputs.outDir.basename)
```

The `outDir` given to such a tool must be an existing directory when the
pipeline starts, as every `Directory` input must; the task works on its copy.
A [Sophios run](#running-on-the-nextflow-target) makes each one that does not
exist yet, as Sophios's CWL runs make an output directory given as a bare
name. The generated pipeline does not, so to run it yourself make each one
first, for example an empty directory under the name `nextflow_params.json`
gives it, in the directory Nextflow is launched from.

An entry with a literal name is named by that literal:

```yaml
requirements:
  InitialWorkDirRequirement:
    listing:
    - entry: $(inputs.source)
      entryname: renamed.txt
arguments:
- cat
- renamed.txt
```

Such an input cannot also be referenced in that tool's command, stream
targets, or output globs; the command names the entry by its literal, as
above.

Rejected: an `entry` that is not a bare reference to one `File` or
`Directory` input (inline content construction), an `entryname` that is any
other expression, holds a `/`, or is `.` or `..`, an `entryname` that begins with
`.sophios_entry_` (the hidden directory's prefix), a `writable` that is not a
literal boolean, a listing entry naming a `val`-qualifier or array-typed
input, an input listed twice, and two entries with one literal name. A name
that collides only when the task runs, such as two entries of inputs with one
basename, or an entry and a staged input with one basename, stops the task
with an error naming the entry.

## Outputs named like staged inputs

Nextflow links each `File` or `Directory` input into the task directory
under its name, so a command that writes that name, or a name inside a
linked directory such as `outdir/listing.txt`, writes through the link into
the file the input names: an upstream task's output, or a workflow input.
Compiling rejects an output whose literal name, a `stdout`, a `stderr` or a
glob with no pattern or reference, is or lies inside a name an input is
linked under that is known before the run: an `InitialWorkDirRequirement`
entry's literal name, or the literal glob of the output the input comes
from. An entry is checked against `stdout` and `stderr` only: a glob that
names an entry collects it, as cwltool does, which is how a tool renames or
passes on a file. A writable entry is the task's own copy, so writing it is
not checked. A name that a workflow input gives, or that a pattern or a
reference makes, is known only when the task runs, and is not checked; give
a tool's outputs names distinct from its inputs' basenames.

## Scatter

A step that scatters over exactly one input runs once per element of its
array-typed source, a workflow input or a gathered scatter output:

```python
echo = Step(echo_tool, step_name="echo_item")
echo.inputs.item = ["alpha", "beta", "gamma"]
echo.scatter_on(echo.inputs.item)
```

The scattered list is split into one indexed invocation per element, so the
process takes one element per task while the step's other inputs stay value
channels and broadcast to every task. Scattering over an empty array runs zero tasks:
the run still terminates and the workflow output is simply empty.

With exactly one scattered input all three CWL methods coincide, so
`dotproduct`, `flat_crossproduct`, and `nested_crossproduct` are each
accepted as inert restatements; any other value is rejected.

Scattering two or more inputs requires an explicit `scatterMethod`:
`dotproduct`, `flat_crossproduct`, or `nested_crossproduct`. The whole
arrays are combined into one invocation per index or per combination — never
by pairing per-element channels, whose pairing would depend on arrival order.

Under `dotproduct` the arrays are paired by index into one invocation per
index. Unequal lengths fail the run, naming each scattered input and its
length; when every array is empty, zero invocations run.

Under `flat_crossproduct` every combination runs, with the first declared
input outermost — CWL's order — so N inputs run the product of their lengths.
Lengths are not compared, and an empty array runs zero invocations.

`nested_crossproduct` runs the same invocations as `flat_crossproduct` and
reports one array dimension per scattered input, in declared order, keeping
empty dimensions; its result reaches workflow outputs only, and feeding it to
a later step is rejected.

Under every method each invocation carries its index as a hidden value
alongside the scattered step's inputs and outputs, and the gather sorts by that
index before stripping it, so the gathered workflow output is always in
invocation order, regardless of which task finishes first. Unscattered inputs,
including File and Directory, still broadcast to every invocation.

The steps that read one workflow input must agree on how its channel is
built: `path` or `val`, the path kind, and whether it carries a list. A
scattered input takes the whole array, so one array input may be scattered at
one step, under any method, and passed whole to another step's array input.

Every scatter, single-input included, carries an invocation index, so its
outputs keep input order at a workflow output and can also feed later steps.
Into an unscattered array-typed input they are gathered once, as one array in
invocation order; each gathered file is staged in its own numbered directory,
so same-named files never collide, and the input receives a list even when a
single file was gathered. A gathered array may itself be a scatter
source. A scattered step may carry a `when`, evaluated per invocation; the
gathered result keeps `null` at each skipped position, so a conditional
scatter's outputs can only reach a workflow output. An unscattered step's
output reaches a scattered step as one value, which every task reads; it is
not an array to scatter over, since no tool output is an array. Scattering
over an array-typed port, over a non-array source, and scattering a nested
workflow step are all rejected.

## Nested workflows

Sophios workflows may contain other Sophios workflows at any resolved nesting
depth. For example:

```python
inner = Step(copy_tool, step_name="inner_copy")
child = Workflow([inner], "child")
inner.inputs.source = child.inputs.source
child.inputs.source = write.outputs.result

root = Workflow([write, child], "root")
```

The core compiler resolves composition, validates workflow boundaries, and
connects each nested input and output before backend lowering. The Nextflow
backend recursively projects the resolved leaf steps as processes, named as
[Names](#names) says. The generated artifacts are flat; nested DSL2
`workflow` blocks are not emitted.

The core semantic pipeline rejects invalid boundary declarations, including
unbound subworkflow inputs and outputs that do not resolve to a child step.
The backend separately rejects executable semantics that would be lost when a
resolved boundary is removed. In particular, `scatter` on a subworkflow call
is not supported. A scattered leaf step *inside* a subworkflow is not a
special case: after projection it follows the scatter rules above.

Workflow-level `ScatterFeatureRequirement`, `SubworkflowFeatureRequirement`,
`MultipleInputFeatureRequirement` and `InlineJavascriptRequirement` (which
Sophios adds for `when`) are accepted as inert declarations, at the outer and
subworkflow level alike; every other workflow-level requirement is rejected by
name.

## Step inputs

A step input written as a `!cwl {...}` record, or a `StepInput` in Python,
may carry `default`, `linkMerge` and `pickValue`. Each is one fixed Groovy
idiom over the step input's values, and none runs JavaScript:

- `default` is the value when the step input has no source, and takes the
  place of a source that is `null`. It is a JSON scalar of the tool input's
  type, which is a `string`, `int`, `float` or `boolean`, and it becomes a
  pipeline parameter named `<step>~<port>` like a tool default.
- `linkMerge` joins the sources in the order the step input names them, one
  source included. `merge_nested` makes a list with one element per source;
  `merge_flattened` splices an array source's elements and adds any other
  source as one element. Two or more sources with no `linkMerge` join as
  `merge_nested`.
- `pickValue` picks from the joined list: `first_non_null` takes the first
  value that is not `null`, `the_only_non_null` the one such value, and
  `all_non_null` the list without its `null`s. `first_non_null` that finds no
  value, and `the_only_non_null` that finds none or several, stop the run
  with `Sophios step input <process>.<port>: <pickValue> finds <n> values
  that are not null`.

Every source is one value: a workflow input, a gathered scatter output, or an
unscattered step's output. Each file of a joined list is staged in its own
numbered directory, as a gathered file is, so same-named files never collide.
A `pickValue` gives a value that is not `null`, so a conditional step's output
may reach any port through one. These are rejected by name: a `default` of a
`File` or `Directory` input; a `pickValue` on one source with no `linkMerge`; a
`default` beside a `linkMerge` or a `pickValue`, which never applies; a
`pickValue` over an array source, since `[]` stands for both `null` and an
empty array; `merge_nested` over an array source, which would nest arrays; a
source that may be `null` in a joined list with no `pickValue`; a scattered
input with any of these fields; and any of them on the input of a nested
workflow step. `label` is documentation. `valueFrom`, `loadContents` and
`loadListing` on a step input are rejected.

## Output cardinality

An `outputEval` of exactly `$(self[0])` is read as a cardinality declaration —
the output carries one value rather than a list — and not as an expression:

```yaml
outputs:
  result:
    type: File
    outputBinding:
      glob: out.txt
      outputEval: $(self[0])
```

It renders as `path 'out.txt', glob: false, arity: '1'`, so the generated pipeline states
the declaration instead of dropping it, emits a single path, and fails the
task when nothing matches. A `File` or `Directory` output whose glob is a
pattern renders `arity: '1'` as well, so several matches fail the task as
they fail in cwltool.

A `path` output declares no kind, and Nextflow does not check `type: 'dir'`
for a literal output name, so a process names its `Directory` outputs in its
`ext` directive instead, `ext Directory: ['<name>']`, which no generated
script reads.

An optional `File?` or `Directory?` output renders `optional: true`; when
nothing matches, a workflow output reports `null`, carried by the `[]`
sentinel. Such an output reaches workflow outputs only: a later step
consuming it, or an optional output of a scattered step, is rejected, since a
`path` port has no lowering of `null` and a gather would drop the position.
An optional output with a pattern glob or a `$(self[0])` capture renders
`arity: '0..*'` instead, since Nextflow fails `arity: '1'` when nothing
matches, even beside `optional: true`. Its workflow output takes the one
file, reports `null` for none, and stops the run with `Sophios workflow
output '<name>' matched <n> files; it takes at most one` for more, as cwltool
fails the step. Such an output must reach a workflow output.

The paired `glob` must be one literal with no `*`, `?`, or `[` and no
`$(inputs...)` reference. `self[0]` is the first of the matched list, which is
a projection only when there is exactly one match by construction; a wildcard
would make CWL's and Nextflow's glob match *ordering* load-bearing, and a
reference's runtime value cannot be shown wildcard-free before the run. Both
are rejected with a diagnostic naming the reason.

Every other `outputEval` text is rejected. `.dirname` and `.path` are
rejected permanently rather than pending: a produced file's directory here is
the Nextflow task work directory, which is never the directory the CWL author
described, so a mapping would run and quietly mean something else. Arbitrary
CWL JavaScript is ruled out by design, so a tool may declare
`InlineJavascriptRequirement` and still be supported as long as it uses only
approved forms.

## File-text capture

`loadContents: true` paired with an `outputEval` of exactly
`$(self[0].contents)`, on a `type: string` output, captures the globbed file's
text as the output value:

```yaml
outputs:
  output:
    type: string
    outputBinding:
      glob: output
      loadContents: true
      outputEval: $(self[0].contents)
```

Both halves are required, and the same literal-glob restriction applies. The
port becomes a `val` output over a generated helper that reads the whole file
from the task work directory, so the pinned CWL v1.2 semantics hold exactly:

- The file is read **entirely**, and a file larger than 65536 bytes fails the
  task. CWL v1.2 replaced v1.0's "read up to the first 64 KiB" with a hard
  limit, so nothing is ever silently truncated.
- A **trailing newline is preserved verbatim**. Nextflow's `eval` output type
  would strip it, so it is not used here.
- The bytes are decoded as UTF-8 **strictly**: malformed input fails the task
  instead of becoming U+FFFD.

`type: int` and `type: float` are rejected: parsing text into a number is
computation, not a projection. Declare `type: string` and parse downstream.

A captured value's only supported sink is a workflow output. Feeding one into
another process is rejected, because every process output before this one
carried the `path` qualifier and the executable graph has no qualifier
agreement check for process edges yet.

## Conditional steps

A `CommandLineTool` step's `when` may be a boolean-typed expression in the
safe JavaScript subset, over the inputs the step binds and its tool declares.
The whole field is one `$( … )`. It may use numbers, `true`, `false`, `null`
and quoted strings; `inputs.<name>` of a `boolean`, `int`, `float` or
`string` input; parentheses; `! - +`; `* / % + -`; `== != === !== < <= > >=`;
`&& ||`; and `Math.abs`, `sqrt`, `floor`, `ceil`, `round`, `pow`, `min` and
`max`. Arithmetic and ordered comparisons take numbers, and `+` never joins
strings. Numbers are binary64 as in JavaScript, so integers are exact only
within ±2^53. A NaN or ±Infinity anywhere in the evaluation, such as a
division by zero, fails the run with an error that names the step, the
expression, the subexpression and the input values. CWL would carry the value
on. Anything outside the subset is rejected by name.

`when` is the only field that may compute. A `valueFrom` on an `arguments`
entry or an `inputBinding` is literal text or a `$(inputs.<name>)` reference
(with `.path` or `.basename` on a `File` or `Directory` input); a computed
`valueFrom` is rejected by name.

A true condition runs the process; a false condition runs no task, and the
step's outputs are `null`, carried by the same `[]` sentinel the
absent-optional lowering uses, so a skipped invocation still emits exactly one
element per output and downstream channels never hang.

A null check on an optional input, `inputs.x === null` or `inputs.x !== null`,
tests for that sentinel too: `=== null` is true for an absent input or for a
skipped upstream step, as in CWL.

That possibly-null value is admitted only where the sentinel is sound: at a
workflow output (which reports `null`), or at an optional `val` input of a
later step whose use the absent-optional lowering already admits (never
referenced, or referenced only as a boolean flag or by its own binding). Every other consumer is
rejected by name — a non-optional port, a `path` consumer, an array-typed
port, or an array-typed output of a conditional step outside scatter.

`when` on a step whose `run` is a workflow is rejected, since skipping an
inlined sub-DAG is not this lowering's single-process shape. A step input the
step's tool does not declare, which CWL allows so that a `when` can read it, is
rejected. A conditional step needs at least one input to gate on, so `when`
on a tool that declares no inputs is rejected.

## The corpus lane

`.github/workflows/nextflow_corpus.yml` compiles corpus workflows with
`--target nextflow`, runs each under Nextflow with Docker, and checks that the
run succeeds and that every declared workflow output exists. It runs every
standalone image-workflows workflow (`bbbc.wic`, `bbbc.py`, `bbbc_sub.py`) and
the standalone mm-workflows workflows the target compiles (`molgan.wic`,
`load_trained_molgan.wic`); the list is in
`tests/core/nextflow/test_corpus.py`. The target rejects the other standalone
mm-workflows workflows: they scatter over a nested workflow step, compute an
output with JavaScript `outputEval`, or declare an optional union of a
`boolean` and a string array.

The lane runs only when dispatched, on a self-hosted Linux runner, since the
tools pull their images and download their data. Dispatch it from the
*Nextflow Corpus* workflow in the Actions tab, or:

```console
gh workflow run nextflow_corpus.yml --ref <branch> \
  -f mm-workflows_ref=main -f image-workflows_ref=main
```

`mm-workflows_owner` and `image-workflows_owner` default to the repository's
owner, and both refs to `main`. The lane runs each pipeline itself, not
through Sophios, so before each run it makes the output directories the
image-workflows tools write into (see Staging with InitialWorkDirRequirement):
an empty directory for every `Directory` input given as a bare name that
names nothing yet.

## Current limits

- Processes must be `CommandLineTool`-equivalent.
- The number types are `int` and `float`. A `long` or `double`, wherever it
  is declared, is rejected by name.
- Fractional CPU requirements reject before lowering; they are not silently
  rounded.

## Field support

Every field the Nextflow target considers is in one of three states.
*Lowered*: the lowering to Nextflow reads it; the note says what it becomes,
and a declaration such as `ScatterFeatureRequirement` becomes nothing of its
own. *Compile-time*: Sophios uses it while compiling, and the Nextflow output
carries nothing for it. *Rejected*: compiling stops, naming the field with the
note as the reason, and writes no artifacts. A field or class missing from
these tables is rejected too, except the document keys Sophios writes:
`$namespaces` and `$schemas` on a tool or workflow, and `sophios:lang_version`
on a workflow, which the Nextflow output carries nothing for. For Sophios's
own classes, the *Sophios* column is what Sophios does with the field when it
compiles to CWL: *native* when Sophios reads it and acts on it, *passthrough*
when it copies it out unchanged, and *rejected* when it refuses it.
