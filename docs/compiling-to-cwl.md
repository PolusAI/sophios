# Compiling to CWL

Everything you have run in this guide went through one translation: Sophios
compiled your workflow into CWL and handed that to a runner. This chapter
opens the base path after a compile, `autogenerated/` under the current
directory unless you moved it with `--basepath`, or `basepath=` in Python,
and reads every file in it, so that you know
why each line is there. It reads the output of the
[first workflow](first-workflow.md), explains the names, and covers the two
ways to package the result and how to run it on a CWL runner of your own.

CWL is one of Sophios's two backends, with [Nextflow](nextflow.md), and it
writes CWL v1.2: one `Workflow` document, one document per step for the tool
or subworkflow it runs, and a job file. Everything on this page is about what
that backend writes;
[The workflow model](workflow-model.md) is what it writes from.

To produce the files without running anything, compile alone, in either
form:

```bash
sophios --yaml greeting.wic --generate_cwl_workflow
```

```python
from greeting import workflow

compiled = workflow().compile()
compiled.write_cwl('autogenerated')
compiled.write_job_inputs('autogenerated')
```

The command line writes the tree below. `write_cwl()` writes the workflow
with every tool embedded in it, as one file, and `write_job_inputs()` the
job file beside it. That one document is what `Workflow.run()` runs.

## The tree

```text
autogenerated/
  greeting.cwl
  greeting_inputs.yml
  greeting~append.cwl
  greeting~cat.cwl
  greeting~touch.cwl
```

`greeting.cwl` is the workflow and `greeting_inputs.yml` its job file. Every
other file is the process one step runs, named `<workflow>~<step>.cwl`, and
sits beside the workflow. A step inside a subworkflow is named by the path
to it, so the [nested pair](subworkflows.md) writes:

```text
autogenerated/
  nested.cwl
  nested_inputs.yml
  nested~cat.cwl
  nested~make_greeting.cwl
  nested~make_greeting~append.cwl
  nested~make_greeting~touch.cwl
```

`nested~make_greeting.cwl` is the subworkflow the step `make_greeting` runs,
and `nested~make_greeting~touch.cwl` the tool its step `touch` runs. Each
file belongs to one step: a tool that three steps run is written three
times, once for each. The workflow's name begins every file, so two
workflows compiled into one base path never overwrite each other's files.
Only the workflow has a job file. A [real-time analysis](realtime-analysis.md)
is laid out the same way, in a directory of its own under `realtime/`.

## The workflow

```yaml
#!/usr/bin/env cwl-runner
# This file was autogenerated using Sophios, version <version>
# https://github.com/PolusAI/sophios
steps:
- id: touch
  in:
    filename:
      source: touch~filename
  run: greeting~touch.cwl
  out:
  - file
- id: append
  in:
    str:
      source: append~str
    file:
      source: touch/file
  run: greeting~append.cwl
  out:
  - file
- id: cat
  in:
    file:
      source: append/file
  run: greeting~cat.cwl
  out:
  - output
cwlVersion: v1.2
class: Workflow
inputs:
  touch~filename:
    type: string
  append~str:
    type: string
outputs:
  touch~file:
    type: File
    outputSource: touch/file
  append~file:
    type: File
    outputSource: append/file
  cat~output:
    type: string
    outputSource: cat/output
```

Read it top to bottom, and each part answers one question:

- `steps:` lists the three steps under the ids you wrote, and for each one
  where every input comes from (`in:`), which file it runs (`run:`), and
  which outputs later steps or the workflow may use (`out:`). `source:` is
  an edge: `touch/file` is the output `file` of the step `touch`.
- `cwlVersion` and `class` make it a standalone CWL v1.2 document that a
  runner can load without Sophios. A workflow whose ports or input files use
  an `edam:` file format also gets `$namespaces`, as
  [What the compiler adds](#what-the-compiler-adds) explains.
- `inputs:` holds the two values you wrote, `greeting.txt` and
  `Hello, Sophios`, as inputs of the workflow; their values are in the job
  file, below.
- `outputs:` exposes every step's outputs, so a run keeps all of them.

Nothing in it is specific to Sophios: the comment at the top names the
Sophios version that wrote the file, and a runner ignores comments. The
version of the `.wic` language the document was read as is printed by the
compile, not written into the file. The rest of this chapter explains why the names look as
they do, where your values went, and what the compiler adds for the
constructs of the later chapters.

### Step names

Each step keeps the id you wrote: `touch` is `touch` in the CWL, and a call
to `make_greeting.wic` is the step `make_greeting`. An id that more than one
step of a workflow has is numbered on every step that has it, the first
included, with `@` and the position you wrote the step at, the number
`(n, id)` names. The [two-appends example](wic-reference.md#21-two-ways-to-write-steps)
compiles to:

```yaml
steps:
- id: touch
  ...
- id: append@2
  ...
- id: append@3
  in:
    str:
      source: append@3~str
    file:
      source: append@2/file
```

and its files are `<workflow>~append@2.cwl` and `<workflow>~append@3.cwl`.
A step whose id is also the name of one of the workflow's inputs or outputs
is numbered the same way, since CWL keeps the three in one namespace, and
ids that differ only in case count as one id. A step inside a subworkflow
is numbered in its own document.

### Names Sophios makes

Where Sophios needs a name you did not write, it joins the step and the
port with `~`: `touch~filename` is the input `filename` of the step `touch`,
and one level down, `make_greeting~touch~file` is the output `file` of the
step `touch` inside the call `make_greeting`. A name you write is made of
letters, digits, `_`, `.` and `-` and does not start with `.` (anything
else is `wic045`), so it never contains `~` or `@`, and a name Sophios
makes can never be one of yours.

### Inputs and the job file

A literal is not written into the CWL. Each becomes a workflow input named
`<step>~<port>`, and its value goes in the job file:

```yaml
touch~filename: greeting.txt
append~str: Hello, Sophios
```

So the CWL is the same whatever values you gave, and a different job file
runs the same workflow on different data. A workflow input you declared keeps
its name; an input inference could not fill is added under its made name
with no value. Before a run, every relative `File` or `Directory` path in
the job is written absolute, so the runner finds it wherever it reads the
job from.

### Edges and outputs

An edge is `<step>/<port>`. A connection you wrote is under `source:`, as
in `greeting.cwl` above; an inferred one is written bare, as
`file: touch/file`. Both mean the same to a
runner.

Every step output is exposed as a workflow output under its made name, and
a named output is added under yours. A Python workflow that names outputs
keeps only those: `Workflow.compile()` returns them and `Workflow.run()`
runs that same document. The command line keeps both. The
[greeting_output pair](connecting-steps.md) begins:

```yaml
outputs:
  greeting:
    type: File
    outputSource: append/file
  touch~file:        # the command line only
    type: File
    outputSource: touch/file
  append~file:
    type: File
    outputSource: append/file
```

### Scatter and conditions

A scattered step carries `scatter` and `scatterMethod` as written, its
outputs are typed as arrays, and `ScatterFeatureRequirement` is added. The
[greet_many pair](scatter-and-conditions.md):

```yaml
requirements:
  ScatterFeatureRequirement: {}
steps:
- id: append
  scatter:
  - file
  - str
  scatterMethod: dotproduct
outputs:
  cat~output:
    type:
      type: array
      items: string
    outputSource: cat/output
```

A conditional step carries `when` as written, and `InlineJavascriptRequirement`
is added. The [greeting_if pair](scatter-and-conditions.md), whose record
binds the workflow input `show` to an input the tool does not declare:

```yaml
requirements:
  InlineJavascriptRequirement: {}
inputs:
  show:
    type: boolean
steps:
- id: cat
  in:
    file:
      source: append/file
    show:
      source: show
  when: $(inputs.show)
```

A `when:` on a subworkflow call reads the names the call takes, such as
`touch~filename`. A `~` cannot appear in `inputs.name`, so write
`$(inputs["touch~filename"])`.

### Records

A record is written as CWL's `WorkflowStepInput`, its sources resolved, and
the requirements it needs added: `MultipleInputFeatureRequirement` for
several sources or a `linkMerge`, `StepInputExpressionRequirement` for a
`valueFrom`, `InlineJavascriptRequirement` for an expression `valueFrom`. The
[record pair](types-and-records.md):

```yaml
requirements:
  MultipleInputFeatureRequirement: {}
steps:
- id: concat
  in:
    files:
      source:
      - touch/file
      - echo/stdout
      linkMerge: merge_flattened
```

### Subworkflows

A subworkflow call is a step whose `run:` is the child's own `.cwl`, and
`SubworkflowFeatureRequirement` is added. The [nested pair](subworkflows.md):

```yaml
requirements:
  SubworkflowFeatureRequirement: {}
steps:
- id: make_greeting
  in:
    touch~filename: make_greeting~touch~filename
    append~str: make_greeting~append~str
  run: nested~make_greeting.cwl
  out:
  - greeting
  - touch~file
  - append~file
- id: cat
  in:
    file:
      source: make_greeting/greeting
```

The child exposes its named output and every inner step output, and the
parent exposes them again with the call's id in front
(`make_greeting~touch~file`).

### What the compiler adds

- `cwlVersion: v1.2` and `class: Workflow`, whatever the document said; a
  `cwlVersion` other than `v1.0`, `v1.1` or `v1.2` is `wic035`.
- `$namespaces` with `edam`, when a `format` of the workflow's inputs or
  outputs, of a File in an input's or a step input's `default:`, or of a File
  in its job file, is an `edam:` CURIE; `edam` then
  means EDAM whatever you bound it to. Every other prefix you declared
  survives; a prefix a promoted port's `format` uses is declared as the tool
  binds it, and two tools that bind one prefix to different URIs for
  promoted ports are `wic031`. Nothing of Sophios's own: the language version
  the document was read under is reported by the compile (`Sophios
  lang_version:` on the command line, `CompiledWorkflow.lang_version` in
  Python), not written into the CWL.
- The requirements the steps need, each only when you did not write it:
  `ScatterFeatureRequirement` for a scatter, `SubworkflowFeatureRequirement`
  for a subworkflow step, `InlineJavascriptRequirement` for a `when` or an
  expression `valueFrom`, `MultipleInputFeatureRequirement` for a record with
  several sources or a `linkMerge`, `StepInputExpressionRequirement` for a
  `valueFrom`.

Everything else you wrote at the top level of a `.wic` document or on a step
(`doc`, `label`, `hints`, `$schemas`, a `requirements:` body) is copied
through as it is;
`inputs` and `outputs` are merged into, the compiler winning on a name
collision. The [language specification](dev/language_spec.md) lists what
happens to each CWL field.

## The tools

Sophios writes descriptions and never touches data. Each tool is written
beside the workflow in a canonical form: `inputs` and `outputs` as mappings
keyed by name, whatever form the source used. Its `cwlVersion` stays what
the file said (`touch.cwl` stays `v1.0`), since each tool is its own
document. A tool given inline under `run:` is written at `v1.2`.

A tool that refers to a file by a path relative to itself means something
only where it was written, so Sophios has cwltool pack it as it writes it:

- an `$include` becomes the text of the file it names, such as a
  `dockerFile` or a script;
- an `$import` becomes the content it names, such as a record type;
- a relative `location` or `path`, as in an input's `default:`, becomes an
  absolute `file://` URI.

The files themselves stay where they are, and Sophios writes nothing beside
them. Take `count.cwl`, with a script beside it and a default that names a
file beside it:

```yaml
requirements:
  InitialWorkDirRequirement:
    listing:
    - entryname: count.sh
      entry:
        $include: count.sh
inputs:
  words:
    type: File
    default: {class: File, location: words.txt}
```

Its step's file in the tree, `words~count.cwl` for a step `count` of
`words.wic`, carries the text of `count.sh` under `entry:` and
`location: file:///home/you/sophios-tutorial/words.txt`. A packed tool is
written in cwltool's own spelling, so other parts may read differently from
what you wrote, such as `requirements` as a list. When cwltool cannot read a
file a tool refers to, the compile stops with `wic013` at the step that runs
it, with cwltool's message.

## Packaging options

Two flags change how the tree is packaged, and neither changes what the
workflow does.

`--cwl_inline_subworkflows` writes one flat workflow: each subworkflow call
that carries nothing but `in` and `out`, whose child is not marked
`wic: inlineable: false`, is replaced by the child's steps, renamed
`<call>~<inner step>` (`make_greeting~touch`); the tools stay separate
files, named the same way (`nested~make_greeting~touch.cwl`). A call that stays
nested is named on stderr with the reason. The root's inputs, outputs and job
file are unchanged.

`--cwl_inline_runtag` writes one self-contained file: every `run:` carries
its process, tools and subworkflows alike, and the shape is unchanged. An
embedded process has no `cwlVersion` of its own, so a v1.0 tool embedded in
the v1.2 workflow would lose the defaults v1.0 gave it; Sophios adds those two
as hints (`NetworkAccess: true`, `LoadListingRequirement: deep_listing`), as
cwltool's own upgrader does, so the tool behaves as it did as a file.
`Workflow.compile()` returns the workflow in this form, with every `run:`
embedded, which is why `compiled.cwl_workflow` is one document, and
`Workflow.run()` runs exactly that document.

Together the two give one flat, self-contained file.

## Running the result elsewhere

The output is standard CWL. To run it with a runner of your own, give it the
workflow and the job file:

```bash
cwltool autogenerated/greeting.cwl autogenerated/greeting_inputs.yml
```

Leave out the job file and cwltool cannot start, because the workflow's
inputs have no values. It says so by printing the inputs the workflow takes,
which are the values you wrote, under the names Sophios made:

```text
...
usage: autogenerated/greeting.cwl [-h] --append~str APPEND~STR
                                  --touch~filename TOUCH~FILENAME
                                  [job_order]
autogenerated/greeting.cwl: error: the following arguments are required: --append~str, --touch~filename
```

To give one on the command line, quote it, `'--append~str' Hello`: zsh
with `extendedglob` set reads an unquoted `~` as a pattern.

Two things to know. A Sophios run writes the job file's relative `File` paths
absolute; a compile-only run leaves them as written, and a CWL runner then
reads them relative to the job file, in `autogenerated/`. And a tool that uses
`cwltool:CUDARequirement` needs cwltool's `--enable-ext`. `--generate_run_script` writes the exact command
Sophios would run, flags included, and `--allow_raw_cwl` lets Sophios itself
run a CWL workflow it did not compile, with its pre-flight and image pulls
([Steps and tools](steps-and-tools.md)).

## Why these choices

- **Literals in the job file** keep the CWL free of data, so a workflow is
  reviewable and reusable as a document and its inputs as another.
- **Your names** are the CWL's names, so the runner's messages, the job file
  and the output object read as the workflow you wrote. Only what Sophios
  makes for you, a literal's input or an exposed output, gets a name you did
  not write: `<step>~<port>`.
- **Every output exposed** means a run keeps everything; a named output is a
  stable handle on top, not a filter.
- **One directory, one file per step** keeps a `run:` a file name, as in
  CWL written by hand, and gives a runner nothing to collide on when it
  copies the tree: cwltool's `--provenance` copies every document a run
  used into one folder by name.
- **Descriptions, not data**: a packed tool reads its scripts and data where
  they are, so compiling never copies or changes a file of yours.

## Recap

The CWL backend writes the workflow, a file per step and a job file into the
base path, each named after the workflow and the step. Steps keep the ids you wrote, every value you
wrote becomes a workflow input with its value in the job file, every step
output is kept as a workflow output, and the requirements the steps need are
added. The result is plain CWL that any CWL runner can run without Sophios.
