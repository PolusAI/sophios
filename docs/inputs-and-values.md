# Inputs and values

Your greeting workflow writes `Hello, Sophios` every time it runs. A real
pipeline is the other way round: the steps stay the same and the data
changes. In this chapter you will turn the greeting into a **workflow
input**, a value the workflow leaves open, give it a value when you run it,
and point a step at a file you already have. Along the way you will meet the
few rules about values that catch people out.

This chapter builds on [Your first workflow](first-workflow.md) and works in
the same `sophios-tutorial/` directory.

Two things changed from `greeting.wic`. The new `inputs:` section declares a

longer has a `!ii` value: `str: message`, with no tag, names that workflow
input. This is why the tag mattered in chapter 1. A tagged value is written
into the workflow; an untagged one names a workflow input.

In Python, save this as `greeting_input.py`:

```{literalinclude} cookbook/greeting_input.py
:language: python
:caption: greeting_input.py
```

`flow.inputs.message` is the workflow input, and assigning it to
`append.inputs.str` both declares it and connects it. The first assignment
gives it the type of the input it feeds, here `string`. Because a workflow
input belongs to the workflow, the script makes the `Workflow` first and
binds the input after.

## Give it a value when you run it

The value comes from an **inputs file**, a YAML file that maps each workflow
input to its value. Save this as `job.yml`:

```yaml
message: Hello from the inputs file
```

Then run either form:

```bash
sophios --yaml greeting_input.wic --inputs_file job.yml --run_local
```

```bash
python greeting_input.py
```

The Python script passes the same file to `run()` in its last line,
`run(run_args_dict={'inputs_file': 'job.yml'})`. In Python a workflow input
can also take its value as you build the workflow:
`flow.inputs.message = 'Hello'` gives it the value an inputs file would, in
the job `compile()` returns and in every run, and an inputs file passed to
`run()` still wins over it. It also says what it did as
you built the workflow:

```text
Adding a new input message to workflow greeting_input
 starting compilation of greeting_input
finishing compilation of greeting_input
...
Success! Runner outputs are under /home/you/sophios-tutorial/autogenerated/outdir_cwltool_greeting_input_2026_10_18_22.21.19/
```

`greeting.txt` in that directory now holds `Hello from the inputs file`, and
`output_greeting_input.json` holds `cat`'s output among the others:

```text
    "cat~output": "Hello from the inputs file\n",
```

Change the line in `job.yml` and run again: the workflow is the same, and
the greeting is new.

### What happens without a value

Run the `.wic` form without `--inputs_file`:

```text
ERROR Workflow error, try again with --debug for more information:
Invalid job input record:
autogenerated/greeting_input.cwl:33:3: Missing required input parameter 'message'
Failure! Above, the first ERROR line, or the error the runner itself raised, says why the run failed.
```

The `ERROR` lines come from cwltool, and the last from Sophios, which sums
up the failure. Sophios does not insist that every workflow input has a
value when it compiles, because the value
may come from anywhere: an inputs file, or a workflow that uses this one as
a step. The runner checks when it starts, before any step runs.

## What Sophios does with your values

Every value you write into a workflow, with `!ii` or by assignment, becomes
an input of the compiled workflow, and the value goes into the **job file**
beside it, `autogenerated/greeting_input_inputs.yml`, which chapter 1 listed
as the values the compiled workflow runs with. The compiled workflow itself
holds no values, so the same CWL runs on other data with another job file.
When you pass an inputs file, Sophios merges it into that job file.

A value must have the type of the input it is given to. Sophios converts
only where nothing is lost: a whole number into a `float` input, a
number or `true`/`false` into a `string` input, which receives its text,
and a string into a `File` or `Directory` input, which receives that string
as its `location`. Anything else is `wic020`, in both forms. In a `.wic` file,
YAML decides the
type of what you write: `!ii 7` is a number and `!ii '7'` is text, and YAML
reads `1e-5` as text, so write a float with a decimal point, `!ii 1.0e-5`.
In Python, the type of the value you assign is the type Sophios sees.

Two more mistakes Sophios reports by name. An input the step's tool does not
have is `wic028` in `.wic` and an `AttributeError` in Python, as chapter 1
showed. Giving one input two values is `wic010` in `.wic`; in Python the
later assignment replaces the earlier one. The
[`.wic` reference](wic-reference.md) has every rule.

## Read a file you already have

Values can be files too. Make a file to read:

```bash
echo "A line I wrote myself" > data.txt
```

and save this pair, which reads it with `cat`:

```{literalinclude} cookbook/cat_file.wic
:language: yaml
:caption: cat_file.wic
```

```{literalinclude} cookbook/cat_file.py
:language: python
:caption: cat_file.py
```

CWL describes a file as a small mapping with `class: File` and the file's
`location`; a directory is the same with `class: Directory`. A bare string
given to a `File` input is read as the `location` of such a mapping, and the
examples write the mapping out. Run either form:

```bash
sophios --yaml cat_file.wic --run_local
```

```bash
python cat_file.py
```

Both succeed, and `output_cat_file.json` holds the line you wrote:

```text
{
    "cat~output": "A line I wrote myself\n"
}
```

### Where a relative path points

`data.txt` is a relative path, and each form reads it from where it was
written:

- a path in a `.wic` file is read from the directory of that file, a
  `default:` included;
- a path in an inputs file is read from the directory of the inputs file;
- a path assigned in Python, given as a `StepInput(default=...)`, or read
  from a step's `step_inputs_file`, is read from the current directory, as
  Python reads any path.

So `sophios --yaml sophios-tutorial/cat_file.wic --run_local` finds
`sophios-tutorial/data.txt` wherever you run it from. A `default:` is
written into the compiled CWL as an absolute path, and so, before a run, is
a value in the job file, so both keep naming the file you meant wherever the
runner reads them; the file itself stays where it is.

Before a run, Sophios checks every file and directory the run will read.
Run `cat_file.wic` with no `data.txt` beside it and the run stops before
anything starts:

```text
error [wic016] input 'cat~file' (from the workflow, whose relative paths are read from /home/you/sophios-tutorial) names 'data.txt', which does not exist at /home/you/sophios-tutorial/data.txt: correct the path, or create the file.
```

The line names the input, where Sophios looked, and why it looked there.

The runner gives a tool its input files read-only. A tool that writes into
its input has to ask for a writable copy in its working directory;
[The CWL you still need](cwl-you-still-need.md) explains how.

## Recap

A workflow input is a value the workflow leaves open: `inputs:` and an
untagged name in a `.wic` file, `flow.inputs.<name>` in Python. An inputs
file gives it a value when you run, with `--inputs_file` on the command line
or `run_args_dict={'inputs_file': ...}` in Python; in Python,
`flow.inputs.<name> = value` gives it one as you build, which an inputs file
overrides. Every value has to fit the
type of its input, and a file is a mapping with `class: File` and a
`location`, read relative to where you wrote it.
