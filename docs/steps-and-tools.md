# Steps and tools

What does a step run, and how does Sophios find it? A step runs a CWL
CommandLineTool, or a [subworkflow](subworkflows.md). This page is about
tools: the ones on your search paths, the ones you name by path, the ones you
build in Python, the ones you write inline, and the plain CWL you already have.

## A tool on the search paths

The common case: the tool exists as a `.cwl` file in a directory Sophios
searches. A `.wic` step names it by file stem, and a Python `Step` by path.

```{literalinclude} cookbook/inline_literal.wic
:language: yaml
:caption: inline_literal.wic
```

```{literalinclude} cookbook/inline_literal.py
:language: python
:caption: inline_literal.py
```

In `.wic`, the step `touch` runs `touch.cwl`. Sophios looks for it on
`search_paths_cwl` from the [configuration](configuration.md): every
directory listed there, recursively, in every namespace. The search is made
once per compile, and every `.cwl` found is read. Two things follow:

- A stem found twice in one namespace prints a warning naming both files and
  the one used. The later definition wins: search paths in the order the
  configuration lists them, then files in sorted path order. To use the other
  file, list its directory later, rename one, or put it in another namespace.
- Nothing under a directory named `autogenerated/` is found, so the tools
  Sophios writes beside its compiled workflows are never mistaken for yours.

A stem that no search path provides is `wic013`, reported at the step:

```text
nost.wic:2:14: error [wic013] process global/nosuchtool is absent from the supplied registry
```

In Python, `Step(clt_path=...)` reads the file at that path, relative to the
working directory, and reads no configuration. A path that does not exist is
`api004`. A `Step` also takes `tool_registry=`, a mapping of tools by stem
and namespace as `sophios.plugins.get_tools_cwl(config)` builds it; when the
path does not exist the stem is looked up there, so a script can name tools
the way `.wic` files do.

`--validate_plugins` makes the command line validate every tool it finds with
cwltool before compiling, which catches a malformed tool at the file that
holds it rather than at the step that runs it.

## A tool named by path

A `.wic` step may name its tool by a path instead of a stem, and a Python step
always does. A `run:` value that ends in `.cwl` or `.wic` is a path, relative
to the document that contains the step; when no file is there, or the value
has neither extension, it is read as a stem and looked up on the search paths.

```{literalinclude} cookbook/word_count.wic

```

Here `word_count.cwl` is a file beside the workflow:

```{literalinclude} cookbook/word_count.cwl
:language: yaml
:caption: word_count.cwl
```

The Python step says `Path(__file__).with_name('word_count.cwl')`, "the file
beside this script", because a Python path is resolved by Python, from the
working directory, and not from the script's location. The step takes its
name from the file stem in both forms, so `count` and `word_count` run the
same tool and the compiled step is `word_count` in both.

## A tool built in Python

The [tool builder](tool-builder.md) makes a `CommandLineTool` object. Two
things take it:

```python
from sophios.api.python.tool_builder import CommandLineTool, Input, Inputs, Output, Outputs, cwl
from sophios.api.python.workflow import Step

word_count = (
    CommandLineTool('word_count',
                    Inputs(text=Input(cwl.file, position=1)),
                    Outputs(counts=Output(cwl.file, glob='counts.txt')))
    .base_command('wc', '-w')
    .stdout('counts.txt')
    .docker('debian:bookworm-slim')
)
count = Step(word_count)              # or
count = word_count.to_step()
```

Both give a `Step` that runs the built tool without any file being written;
the compiled workflow carries the tool as `<step>.cwl` under `autogenerated/`
like any other. `to_step(step_name=..., step_inputs={...})` names the step and
binds inputs in one call. A `.wic` file has no spelling for a tool built in
memory; write the tool out with `word_count.write_cwl('word_count.cwl')`, and
a `.wic` step runs the file, by path as above or by stem from a search path.

## A tool written inline

A `.wic` step may carry its tool's whole CWL under `run:`, and Python builds
the same step from a mapping with `Step.from_cwl_document`:

```{literalinclude} cookbook/record.wic
:language: yaml
:caption: record.wic
```

```{literalinclude} cookbook/record.py
:language: python
:caption: record.py
```

The inline body is written out as its own tool file beside the compiled
workflow, like any other tool, at the workflow's CWL version: a `cwlVersion`
inside the body is ignored, as CWL requires of a process embedded in a
workflow. `from_cwl_document(document, process_name=..., run_path=...,
step_inputs=...)` names the step (the document's `id`, or `in_memory_tool`,
when it is not given), the `.cwl` path the compiler records, and the inputs
to bind. For a tool you will use more than once, the tool builder is the
better spelling of the same thing.

## The same tool twice

A step is named for its tool, and names in a workflow are unique, so a tool
that appears twice needs a name of its own for each step:

```{literalinclude} cookbook/renamed_step.wic
:language: yaml
:caption: renamed_step.wic
```

```{literalinclude} cookbook/renamed_step.py
:language: python
:caption: renamed_step.py
```

In `.wic`, `steps:` written as a mapping cannot repeat a key, so write it as a
sequence: each entry carries `id:` with the step's name and `run:` with the
tool's stem or path. The sequence form is also the one to use when a repeated
tool keeps its own name, as the two `append` steps of `multistep1.wic` do; a
step name may repeat in the sequence form, and the compiled CWL tells them
apart by position. In Python, `step_name=` names the step, and a repeated name
in one workflow is `api002`. The step names reach the compiled CWL as they
are: `hello` and `goodbye`.

## What a `.cwl` file may hold

A tool file is one `CommandLineTool`. It may also be a packed document, a
`$graph` whose `main` entry is a CommandLineTool: Sophios runs `main`, as a
CWL runner would, and reads its `cwlVersion`, `$namespaces` and `$schemas`
from the top of the packed file. A packed document with no `main` is
`wic013`.

A `.cwl` file whose class is `Workflow` cannot be a step, whether it was found
by stem, named by `run:`, or written inline (`wic013`). Write it as a `.wic`
subworkflow and call that, or run the CWL workflow on its own, as the next
section describes.

## Plain CWL passes through

A workflow that is already CWL is not a Sophios document, and Sophios does not
compile it:

```bash
sophios --yaml workflow.cwl --allow_raw_cwl --run_local --inputs_file job.yml
```

With `--allow_raw_cwl`, a `--yaml` file whose top level has `cwlVersion` and
`class: Workflow` (or a packed `$graph` whose `main` is a Workflow), with no
Sophios syntax in it (no `!ii`, `!&`, `!*` or `!cwl` tag and no top-level
`wic:`), is given to the runner as it is. The `--inputs_file` is its job file,
also given as it is, so each resolves its relative paths against its own
directory; without one the runner gets no job file and the workflow's defaults
apply. Nothing is parsed, copied or rewritten:

- `--run_local`, `--generate_run_script` and `--check` work as for a compiled
  workflow, pre-flight included;
- `--generate_cwl_workflow` writes nothing and says so;
- `--graphviz` draws only cwltool's SVG of the file;
- the flags that rewrite compiled CWL (`--cwl_inline_runtag`,
  `--cwl_inline_subworkflows`, `--partial_failure_enable`,
  `--docker_remove_entrypoints`) are an error.

The CWL Sophios writes is itself plain CWL. After compiling `greeting.wic`,
this runs the result without compiling again:

```bash
sophios --yaml autogenerated/greeting.cwl --inputs_file autogenerated/greeting_inputs.yml --allow_raw_cwl --run_local
```

The Python API builds workflows; it has no call that takes a finished CWL
workflow. Run one with the command line.

`--allow_raw_cwl` has a second meaning when the file is a Sophios document:
an untagged input value that names no workflow input is then written into the
CWL unchecked instead of being `wic011`. [Inputs and values](inputs-and-values.md)
covers the forms an input value takes.
