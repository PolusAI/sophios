# Steps and tools

Most steps so far have run one of the tools that ship with Sophios, named by
its file name; the last chapters also used a few small tool files beside the
workflow, named with `run:`. Your own pipelines will run programs Sophios has
never heard of, and some will run one program twice. In this chapter you will
see where Sophios looks for a tool, write a second line into the greeting with
the same tool used twice under two names, and see how a tool file that sits
beside your workflow, such as the word counter, is written and named.

## Where Sophios finds a tool

A `.wic` step names its tool by file name without the extension: `touch`
means `touch.cwl`. Sophios looks for it in the directories listed under
`search_paths_cwl` in its configuration, `~/wic/global_config.json`, which
[Install](install.md) wrote with one directory, `~/wic/cwl_adapters/`.
Every directory is searched recursively, and every `.cwl` file found there
can be named by its stem. To use tools of your own by name, add their
directory to that list; [Configuration](configuration.md) shows how.

A name no search path provides stops the compile at the step. Name a tool
that does not exist, such as `- id: append_line` where you meant `append`,
and Sophios says:

```text
typo.wic:5:3: error [wic013] process global/append_line is absent from the supplied registry
```

The registry is the set of tools the search paths provided, and `global` is
the namespace the name was looked up in; [Configuration](configuration.md)
explains namespaces, which keep two tool collections apart.

The same stem in two directories is a warning that names both files and the
one used. Sophios never reads what it generated as a tool of yours: it skips
every directory named `autogenerated/` below a search path, and the base path
in use when it lies inside one.

The Python API reads no configuration. `Step(clt_path=...)` loads the file
at that path, which is why the Python examples keep the directory of the
shipped tools in a constant, `ADAPTERS = Path.home() / 'wic' / 'cwl_adapters'`,
and add a file name to it for each step. A relative path is read from the
current directory.

## Use one tool twice

To write a second line into the greeting, run `append` twice. In a workflow
every step needs its own name, and so far a step's name has been its tool's
name. Give each step a name of its own and say which tool it runs:

```{literalinclude} cookbook/two_lines.wic
:language: yaml
:caption: two_lines.wic
```

```{literalinclude} cookbook/two_lines.py
:language: python
:caption: two_lines.py
```

In `.wic`, `id:` is now the step's name and `run: append` names the tool,
found by name as before. In Python, `step_name=` names the step. Both forms
leave the connections to [edge inference](edge-inference.md), which
connects each step to the file the step before it made. Run either form:

```bash
sophios --yaml two_lines.wic --run_local
```

```bash
python two_lines.py
```

The command line notes two choices, since each later step had more than one
file to choose from:

```text
two_lines.wic:9:3: note [wic043] step 'goodbye' input 'file' was inferred from the most recent match step 2 'hello' output 'file'; earlier steps also match: step 1 'touch' output 'file'; pin it: `out: - file: !& <name>` on step 2 'hello' and `in: file: !* <name>` here (step 3 'goodbye', port 'file')
two_lines.wic:13:3: note [wic043] step 'cat' input 'file' was inferred from the most recent match step 3 'goodbye' output 'file'; earlier steps also match: step 2 'hello' output 'file', step 1 'touch' output 'file'; pin it: `out: - file: !& <name>` on step 3 'goodbye' and `in: file: !* <name>` here (step 4 'cat', port 'file')
```

Both are the choices you want, and `greeting.txt` holds both lines:

```text
Hello, Sophios
Goodbye for now
```

The step names reach the compiled workflow and every message about it:
`hello` and `goodbye`. In Python, two
steps of one workflow with the same name are `api002`. A `.wic` file may
repeat an id in its list of steps, and Sophios tells the steps apart by
position, but a reader cannot, and [Converting](converting.md) to Python
refuses it; give each step its own name.

## Add a tool of your own

Here is the word counter from [Connecting steps](connecting-steps.md), a
tool file that runs `wc -w` in a small Debian image. It is saved as
`word_count.cwl` in your project:

```{literalinclude} cookbook/word_count.cwl
:language: yaml
:caption: word_count.cwl
```

A step can name a tool by path instead of by name. In `.wic`, a `run:` value
that ends in `.cwl` is a path, read relative to the `.wic` file:

```{literalinclude} cookbook/word_count.wic
:language: yaml
:caption: word_count.wic
```

```{literalinclude} cookbook/word_count.py
:language: python
:caption: word_count.py
```

The Python step uses `Path(__file__).with_name('word_count.cwl')`, the file
beside the script, because Python reads a relative path from the current
directory, not from the script's. Run either form:

```bash
sophios --yaml word_count.wic --run_local
```

```bash
python word_count.py
```

The command line notes that it connected the counter's `text` to the file
`append` wrote:

```text
word_count.wic:8:3: note [wic043] step 'word_count' input 'text' was inferred from the most recent match step 2 'append' output 'file'; earlier steps also match: step 1 'touch' output 'file'; pin it: `out: - file: !& <name>` on step 2 'append' and `in: text: !* <name>` here (step 3 'word_count', port 'text')
```

The output directory holds `counts.txt`, which reads `2` followed by the
path `wc` was given: two words, `Hello,` and `Sophios`. The step takes its
name from the tool's file in both forms, so it is
`word_count` in the compiled workflow.

Which to use? Name a tool by stem when it lives in a shared collection on
the search paths, so the workflow runs on any machine whose configuration
lists that collection. Name it by path when the tool belongs to this
project and travels with the workflow, as `word_count.cwl` does here.

You do not have to write tool files by hand. [Writing tools in
Python](tool-builder.md) builds this same tool in a few lines of Python, and
writes the file for you.

## Other places a tool can come from

A `.wic` step may carry its tool's whole CWL under `run:`, and Python builds
the same step from a mapping with `Step.from_cwl_document()`. That suits a
one-off tool; [Types and records](types-and-records.md) uses one. The inline
tool is written out as its own file beside the compiled workflow.

A tool file holds one CWL `CommandLineTool`, or a packed document whose
`main` entry is one. A file whose class is `Workflow` cannot be a step
(`wic013`): call it as a `.wic` subworkflow instead, or run it on its own as
the next section shows.

## Run a CWL workflow you already have

A workflow that is already CWL needs no compiling, and Sophios will run it
for you with the same checks and image pulls as one of its own. The CWL that
Sophios writes is such a workflow. After a compile of `greeting.wic`, this
runs the result without compiling again:

```bash
sophios --yaml autogenerated/greeting.cwl --inputs_file autogenerated/greeting_inputs.yml --allow_raw_cwl --run_local
```

With `--allow_raw_cwl`, a file whose top level is a CWL `Workflow` and that
holds no Sophios syntax is handed to the runner as it is, with the inputs
file as its job file. Nothing is parsed, rewritten or copied, so the flags
that rewrite compiled CWL, such as `--partial_failure_enable`, are an error
here. Under `--target nextflow` the file is compiled like any other workflow.
The Python API builds workflows and has no call that takes a finished
CWL workflow; use the command line. The
[command-line reference](cli-reference.md) lists what each flag does in this
mode.

## Recap

A `.wic` step names its tool by stem, found on the configuration's search
paths, or by path with `run:`; a Python step names it by path. To use one
tool twice, give each step its own name: `id:` and `run:` in `.wic`,
`step_name=` in Python. A tool file of your own can sit beside the workflow,
and a CWL workflow you already have runs as it is with `--allow_raw_cwl`.
