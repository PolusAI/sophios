# Running workflows

This page is about running a workflow the way you need: checking first,
choosing where the results go, using another container engine or runner,
running on a cluster, reusing results from an earlier run, following a run
from Python, and preparing a run to start later. The machine you run Sophios on can be your laptop, a
cloud instance or a lead compute node of an HPC cluster, never its login node.
Every task works the same for a `.wic` file and a Python workflow; each one
shows both.

## Before you begin

You need a machine set up as in [Install](install.md), and a workflow that
compiles, such as the `greeting` pair from
[Your first workflow](first-workflow.md).

## What a run does

A local run goes through four stages, in the same order from either form:

1. **Compile.** Sophios checks the workflow and writes it as CWL into the
   base path.
2. **Check the machine.** Sophios checks what the run needs from this
   machine: the container engine, the input files, the directories it
   writes to and the programs it calls. It reports every problem at once,
   before anything is pulled.
3. **Fetch the images.** Every container image the tools name is pulled, so
   the run starts with all of them present.
4. **Run.** Sophios hands the compiled workflow to a runner, cwltool unless
   you choose Toil, and reports how it ended.

Each command stops after a different stage:

| To | Command line | Python |
|---|---|---|
| compile only | `sophios --yaml w.wic --generate_cwl_workflow` | `flow.compile()` |
| compile and check the machine | `sophios --yaml w.wic --check` | none; `run()` checks before it runs |
| prepare a run to start later | `sophios --yaml w.wic --generate_run_script` | `flow.run(run_args_dict={'generate_run_script': 'yes'})` |
| run | `sophios --yaml w.wic --run_local` | `flow.run()` |
| run, and get on with something else | none | `flow.start()`, or `await flow.run_async()` |

The command line needs exactly one of these. In Python, options go in
`run()`'s `run_args_dict`, a mapping from flag names, without the dashes, to
strings; [The same options from Python](cli-reference.md#the-same-options-from-python)
lists them.

## Check before a long run

To find out whether a run would start, without writing, pulling or running anything:

```bash
sophios --yaml greeting.wic --check
```

```text
Checked greeting: nothing in the way of a local run on this machine. Nothing was written, pulled or run.
```

Run it on a new machine, or before a run that will take hours. A problem is
one line with a code and what to do, such as `wic015` for a container engine
that is not running or `wic016` for an input file that does not exist;
[Checks and errors](checks-and-errors.md) explains each kind. `Workflow.run()`
makes the same checks before it starts.

## Choose where the results go

Sophios keeps everything about a run under its base path, `autogenerated/`
under the current directory by default. The run's output files go into a new
directory inside it, named for the runner, the workflow and the time.

- To choose another base path, pass `--basepath <dir>` on the command line, or
  `basepath='<dir>'` to `run()`; a relative path is read from the current
  directory. Everything Sophios generates goes there: the compiled workflow
  and job file, the record of the run, `output_<workflow>.json`, the run's
  log `run_<workflow>.log`, the output files, and, on the command line, the
  drawings and the schema. Only `run.sh`,
  `error_<workflow>.txt` and, when a real-time analysis turns caching on
  without `--cachedir`, `cachedir/` stay in the current directory.
- To put only the output files somewhere else, pass `--outdir <dir>`, or
  `run_args_dict={'outdir': '<dir>'}`. The rest stays in the base path.

```bash
sophios --yaml greeting.wic --run_local --basepath build --outdir results
```

```python
from greeting import workflow

workflow().run(basepath='build', run_args_dict={'outdir': 'results'})
```

Both directories are checked before anything is compiled into them. One
Sophios cannot create or write to stops the run:

```text
error [wic021] Sophios writes the compiled workflow to /no_such_root_dir/build, but / is not writable by you: give --basepath a directory you can write to.
```

When the base path lies inside one of your search paths, Sophios never reads
the files it generated there as tools or workflows of yours.

## Choose a container engine

Docker is the default. To use another engine, name it:

```bash
sophios --yaml greeting.wic --run_local --container_engine podman
```

```python
workflow().run(run_args_dict={'container_engine': 'podman'})
```

| Engine | What changes |
|---|---|
| `docker` | nothing; the default |
| `podman` | images are pulled with podman, and the runner is told to use it |
| `singularity` | images are pulled as Singularity images into `--pull_dir` (the current directory unless you name one), and the runner is told to use Singularity |

A tool that names no container, such as `append.cwl`, runs directly on your
machine whatever the engine, and needs its program installed there.

## Choose a runner

cwltool runs workflows by default. To run the same compiled workflow with
Toil, which can also send jobs to a cluster:

```bash
sophios --yaml greeting.wic --run_local --cwl_runner toil-cwl-runner
```

```python
workflow().run(run_args_dict={'cwl_runner': 'toil-cwl-runner'})
```

Toil keeps its state in a job store, `jobStore_<workflow>` in the base path,
instead of a cache. Flags for the runner itself pass through: on the command
line add `--passthrough_flags yes`, and in Python put them in
`run_args_dict`, where every key Sophios does not use becomes
`--<key> <value>` for the runner; `{'logLevel': 'INFO'}` reaches Toil as
`--logLevel INFO`.

### Run on a cluster

Toil can send each step to a cluster's scheduler instead of running it on
the machine you started from. Choose the scheduler with Toil's own
`--batchSystem` flag, passed through Sophios, for example `slurm` or `lsf`:

```bash
sophios --yaml greeting.wic --run_local --cwl_runner toil-cwl-runner --passthrough_flags yes --batchSystem slurm
```

```python
workflow().run(run_args_dict={'cwl_runner': 'toil-cwl-runner', 'batchSystem': 'slurm'})
```

Three things to know. Sophios still makes its checks and pulls the images
on the machine you start it from, before Toil starts, so the machine you
start from needs the container engine, and so do the nodes the scheduler
runs the steps on; on most clusters that is Singularity, with
`--container_engine singularity`. Toil keeps its job store in the base path,
and the scheduler's nodes must be able to read it, so start from a directory
on the cluster's shared filesystem. And when the flags you pass mention
`slurm`, Sophios leaves out the `--provenance` record it otherwise asks Toil
for. Toil's documentation is the authority for each scheduler's flags; what
Sophios adds is listed here.

## Reuse results from an earlier run

cwltool can keep each step's results and reuse them when the same step runs
again with the same tool and inputs. Ask for a cache directory:

```bash
sophios --yaml greeting.wic --run_local --cachedir cache
```

```python
workflow().run(run_args_dict={'cachedir': 'cache'})
```

There is no cache unless you ask for one. Toil ignores it, since it has its
job store. A [real-time analysis](realtime-analysis.md) needs the cache and
turns it on, in `cachedir/`, unless you named a directory.

## See more, or less, of the run

The command line shows cwltool's log of every step, each command it ran and
how each ended, and what each tool prints. Add `--quiet` to hide cwltool's
own log; what each tool prints still shows as the run goes. Python is quiet
by default; pass `run_args_dict={'quiet': 'no'}` to see the log. `--quiet`
changes only what the runner prints: the compiled CWL is the same with or
without it.

In Python, `quiet`, `no_provenance`, `generate_run_script` and
`docker_remove_entrypoints` are yes/no switches: `yes`, `true`, `1` and `on` turn one on. The last is a
diagnostic, not a setting for everyday runs; the
[section on entrypoints](#images-that-rely-on-an-entrypoint) explains it.

## Give tools an environment variable

A tool does not see your shell's environment. A tool that needs a variable
declares it in its own description, as
[The CWL you still need](cwl-you-still-need.md) shows. From Python,
`run(user_env_vars={'NAME': 'value'})` adds variables to the environment the
runner starts in, which tools that run directly on your machine also see. A
key that is not a valid variable name is a `ValueError`.

## Prepare a run to start later

`--generate_run_script` compiles, checks, pulls the images, and then writes
the exact runner command to `run.sh` in the current directory instead of
running it:

```bash
#!/bin/bash -e
# This file was autogenerated using Sophios, version <version>
# https://github.com/PolusAI/sophios
cwltool_filterlog --disable-pull --provenance /home/you/sophios-tutorial/autogenerated/provenance/greeting --write-summary /home/you/sophios-tutorial/autogenerated/output_greeting.json --skip-schemas --relax-path-checks --move-outputs --enable-ext --outdir /home/you/sophios-tutorial/autogenerated/outdir_cwltool_greeting_2026_10_18_22.24.15 /home/you/sophios-tutorial/autogenerated/greeting.cwl /home/you/sophios-tutorial/autogenerated/greeting_inputs.yml
```

Run it later on this machine, or read it to see what a run does.
`cwltool_filterlog` is cwltool, started with two noisy log messages
filtered out. The compiled workflow and job file it names are standard CWL,
so a CWL runner on another machine needs only them, the step files beside
them, and the files the job and the tools name. To send a workflow to a separate compute
service instead, see [The compute client](compute.md).

## Images that rely on an entrypoint

A runner starts a container with the tool's command line as the arguments of
the image's `ENTRYPOINT`, when the image has one. A tool that works only
because of an entrypoint will not run anywhere else: not on the host, not
with another build of the image, and not under another runner. The
[CWL forum's advice](https://cwl.discourse.group/t/override-docker-entrypoint-in-command-line-tool/695/2)
is plain: do not rely on `ENTRYPOINT`; give the tool a `baseCommand`, and
`arguments` where needed, that names the program.

`--docker_remove_entrypoints`, or `{'docker_remove_entrypoints': 'yes'}` in
Python, finds the tools that break that advice. It was built for the
continuous integration of Sophios's own tool collections, where the same
tools must run both in their released images and on the host from the
latest code, and an entrypoint makes the two behave differently. With the
flag, before a local run, Sophios rebuilds every tagged image on your
machine, not only the workflow's, as a copy tagged `<tag>-noentrypoint`
whose entrypoint is removed, and points the compiled tools at those copies.
A tool with no `baseCommand` or `arguments` of its own then fails, which is
what you wanted to find out.

Use it as a diagnostic, never as a way to run workflows. It rebuilds every
local image on each run, leaves the copies behind, works only with Docker
and Podman, and acts only on a local run. The copies are tagged images, so
`docker image prune` without `-a` keeps them; to remove them, delete them by
tag, `docker image rm <image>:<tag>-noentrypoint`. The fix for a tool the
flag exposes is in the tool: a `baseCommand` that does not depend on the
image's entrypoint.

## What a run leaves behind

Everything goes into the base path:

| Path | What |
|---|---|
| `<workflow>.cwl`, `<workflow>_inputs.yml` | the compiled workflow and its job file; from Python, or with `--cwl_inline_runtag`, the workflow is one document with every step's process in it |
| `<workflow>~<step>.cwl` | on the command line, the tool or subworkflow each step runs, one file per step ([Compiling to CWL](compiling-to-cwl.md#the-tree)) |
| `outdir_<runner>_<workflow>_<time>/` | the run's output files, unless `--outdir` names another place |
| `output_<workflow>.json` | every workflow output with its value; Toil prints it, and Sophios writes it here as cwltool does |
| `run_<workflow>.log` | everything the runner printed, both streams, as the run went |
| `provenance/<workflow>/` | the runner's record of what ran, with what, and what came out |
| `realtime/`, `<workflow>.realtime.json` | compiled real-time analyses, when the workflow declares any |

`run.sh` and, after a failure Sophios did not expect, `error_<workflow>.txt`
with the full traceback, go into the current directory.

The record in `provenance/<workflow>/` is a research object, cwltool's and
Toil's account of the run: every document the run used, each step file
included, the job, and what each step produced. To run without it, pass
`--no_provenance`, or `run_args_dict={'no_provenance': 'yes'}` in Python.

When one document refers to two different data files with the same name (most often a single-document run, `--cwl_inline_runtag` or `Workflow.run()`; in the tree, when one tool with two data defaults, the second a directory, is run by two steps), the run finishes and writes its outputs, and only writing the record fails, with exit code 1.
This happens under cwltool and toil-cwl-runner alike, and the fix is in cwltool ([cwltool#2370](https://github.com/common-workflow-language/cwltool/pull/2370), for [issue #2369](https://github.com/common-workflow-language/cwltool/issues/2369)).
Until it ships, pass `--no_provenance`, or `run_args_dict={'no_provenance': 'yes'}`.

## Follow a run from Python

`run()` waits for the run and returns how it ended. `start()` returns as
soon as the runner has started, with a handle to follow the run by;
`run_async()` is `run()` for code that runs in an event loop. All three take
the same arguments, and do the same work before the runner starts: they
compile, check the machine and pull the images, and raise what those raise.

### What run() returns

`run()` returns a `RunResult`, from `sophios.api.python.workflow`:

```python
from greeting import workflow

result = workflow().run()
print(result.outputs['cat~output'], end='')   # Hello, Sophios
print(result.outdir)                           # where the output files are
print(result.log_file)                         # everything the runner printed
```

| Field | What |
|---|---|
| `state` | `RunState.COMPLETED`: a run that ends any other way raises |
| `outputs` | the workflow's outputs, as `output_<workflow>.json` holds them |
| `outdir` | the directory the output files were moved to |
| `log_file` | `run_<workflow>.log` in the base path |
| `exit_code` | the runner's, `0` |

A run that fails still raises `WorkflowRunError`
([When a run fails](#when-a-run-fails)), so a script that ignores what
`run()` returns behaves as it did. With `generate_run_script`, nothing runs
and `run()` returns `None`.

### Start a run and come back to it

```python
from greeting import workflow

run = workflow().start()
print(run.status().state)       # RunState.RUNNING
# ... do something else ...
status = run.wait()             # how it ended; nothing is raised
result = run.collect()          # its RunResult, as run() returns it
print(status.state, result.outputs)
```

`start()` returns a `RunHandle`, once the runner has started. Its methods
can be called from any thread:

| Method | What it does |
|---|---|
| `wait(timeout=None)` | blocks until the run ends and returns its `RunStatus`; after `timeout` seconds it raises `TimeoutError` and the run goes on. A run that failed or was cancelled is returned, not raised. Once the run has ended, it returns the same status at once |
| `collect(timeout=None)` | `wait()`, then the run's `RunResult`, as `run()` returns it: a run that failed or was cancelled raises `WorkflowRunError`. `run()` is `start().collect()` |
| `status()` | where the run is, without blocking: a `RunStatus` with `state`, `reason`, `started_at`, `ended_at`, the failed `steps`, `outputs` and `exit_code` |
| `logs()` | everything the runner has printed so far |
| `outputs()` | the workflow's outputs once the run has completed; `None` until then |
| `cancel()` | stops the runner as Ctrl-C does, and the run ends `CANCELLED`; returns `True`, as it does when the run was cancelled already. A runner that has already exited is reported as it ended, `COMPLETED` or `FAILED`, and `cancel()` returns `False` |

The states are those the [compute service](compute.md) reports:

| State | Meaning |
|---|---|
| `QUEUED` | accepted and not started yet. A local run is never seen in it: `start()` returns once the runner has started |
| `RUNNING` | the runner is running |
| `COMPLETED` | the runner exited 0; `outputs()` holds the outputs |
| `FAILED` | the runner exited non-zero, or could not be started; `status().steps` names the failed steps |
| `CANCELLED` | `cancel()`, or Ctrl-C during `wait()` or `collect()`, stopped it |

The last three never change. The runner is a child of your Python process,
and the run lives as long as that process does: there is no detaching from
it. When the interpreter exits with the run still going, at the end of the
script, on `sys.exit()` or an uncaught exception, the run is cancelled; a
run whose runner has exited is reported on then, if nothing did before. A
Python process killed by a signal (`kill`, `kill -9`) cannot stop its
runner. `start()` does not write `run.sh`; pass `generate_run_script` to
`run()` for that.

### Run from asyncio

`run_async()` is a coroutine with `run()`'s arguments and result. The
compile, the checks and the image pulls run in a worker thread, and the
runner is awaited without blocking the event loop, so other tasks keep
running:

```python
import asyncio

from greeting import workflow


async def main() -> None:
    result = await workflow().run_async()
    print(result.outdir)


asyncio.run(main())
```

Cancelling the task that awaits it stops the runner, as `cancel()` does,
before the cancellation goes on; Ctrl-C under `asyncio.run` does the same.
Cancelled while the worker thread is still compiling, checking or pulling
images, the task ends at once and nothing is run, but the thread finishes
its work first, since a thread cannot be stopped from outside:
`asyncio.run` returns only after it. A failed run raises
`WorkflowRunError`, as from `run()`.
`run_async()` never runs [real-time analyses](realtime-analysis.md): a
workflow that declares one is refused with `api008`, before anything is
written or run. Use `run()` or `start()` for it; from a coroutine,
`await asyncio.to_thread(flow.run)` keeps the event loop free.

## When a run fails

A run that succeeds ends with `Success! Runner outputs are under ...`. One
that fails ends with a `Failure!` line for each step that failed, naming the
step as it is called in the compiled workflow, with its exit status:

```text
Failure! step 'fail' exited with status 1. Its own messages are above, under its name.
```

For statuses 126, 127 and 137 the line also says what they usually mean: the
command could not be executed, was not found, or was killed, usually for
memory. The step's own messages are above it in the log. The command line
exits with the runner's exit code, and `Workflow.run()` and
`Workflow.run_async()` raise `WorkflowRunError`, whose `exit_code` is the
runner's.

The runner runs as a separate program, a child of Sophios. What it prints
shows as it comes, in a terminal and in a notebook alike, and is kept in
`run_<workflow>.log` in the base path. Ctrl-C stops Sophios, which then stops
the runner: it sends the runner SIGTERM, on which cwltool stops the
containers it started, and kills the runner and everything it started if it
has not stopped within 30 seconds. Toil stops its own jobs, but a container
one of them started can keep running: `docker ps` shows it, and
`docker kill <id>` stops it. The command line exits with 130, and Python
raises `KeyboardInterrupt`; a run started with `start()` is stopped the same
way by `cancel()`.
However else Sophios ends (`kill`, a closed terminal or SSH session, a
restarted notebook kernel, even `kill -9`), the runner is stopped the same
way: a small watcher started beside it sees that Sophios has gone, sends the
runner SIGTERM, and kills it if it has not stopped within 30 seconds. A run
started under `nohup` keeps going after you log out.
[Checks and errors](checks-and-errors.md) shows how to read each kind of
problem.
