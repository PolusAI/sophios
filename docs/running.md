# Running workflows

How do I run a workflow on this machine, choose the runner and the container
engine, and find what the run wrote? A local run has four stages: compile,
check the machine, pull the images, run the CWL with cwltool or Toil. The
command line and `Workflow.run()` go through the same four, and this page
covers what each stage does, the options that change it, and the files it
leaves under `autogenerated/`.

## The commands

| Do | Command line | Python |
|---|---|---|
| Compile only | `sophios --yaml w.wic --generate_cwl_workflow` | `flow.compile()`, then `write_cwl()` and `write_job_inputs()` |
| Compile and check the machine | `sophios --yaml w.wic --check` | no equivalent; `run()` checks before it runs |
| Compile, check, pull, write `run.sh` | `sophios --yaml w.wic --generate_run_script` | `flow.run(run_args_dict={'generate_run_script': 'yes'})` |
| Compile, check, pull, run | `sophios --yaml w.wic --run_local` | `flow.run()` |

The command line needs exactly one of the four; without one it compiles and
then says so. In Python, `run()` compiles the workflow itself, writes it under
`basepath` (`autogenerated/` by default), and runs it; the options go in
`run_args_dict`, a mapping of command-line flag names to values, with `yes`
and `no` for the switches. `run()` returns `None` on success and raises
`WorkflowRunError`, whose `exit_code` is the runner's, when the runner exits
non-zero. Ctrl-C raises `KeyboardInterrupt`; with cwltool the runner's child
processes are terminated first.

## The pre-flight

Before anything is pulled or run, Sophios checks what the run needs from this
machine, and reports every problem at once, one line each, with a code and
what to do:

- the container engine, when a step runs in a container: installed, its
  daemon reachable (`docker info` or `podman info` succeeds), its socket
  yours to use, and, for Docker Desktop, not more than 1000 `com.docker`
  processes running, which can make a run hang (`wic015`);
- every `File` and `Directory` a job names: it exists, is the right kind, and
  is readable (`wic016`);
- the directories Sophios writes into: `autogenerated/` under the working
  directory, `--outdir`, and `run()`'s `basepath` and `outdir` (`wic021`);
- the programs the run calls: `cwl-docker-extract` when images are to be
  pulled, `cwltool_filterlog` or `toil-cwl-runner` when `run.sh` is to be
  written, and the runner itself, which cannot run on Windows outside WSL
  (`wic029`).

`--check` stops here and prints that nothing is in the way. The checks are
made for local runs only, and `--ignore_docker_install` and
`--ignore_docker_processes` skip the first two engine checks for a machine you
know better than Sophios does.

## Pulling images

Every `DockerRequirement` of every process the run uses is pulled before the
run, by `cwl-docker-extract`, with the engine you chose, and the runner is
then told not to pull (`--disable-pull`). The pull is forced, so an image
that exists locally under the same name is refreshed from its registry; an
image that exists only on your machine fails the pull. For such an image a
tool declares `dockerImageId` alone, which the pull skips and the runner uses
as it is. An image a tool ships as `dockerLoad` (a file or an http(s) URL) or
`dockerImport` is loaded or imported into the engine instead, and a
`dockerFile` is left to cwltool, which builds it at run time. A pull, load or
import that fails stops the run with `wic037`, quoting the engine's last
line. With Singularity, images are pulled into `--pull_dir` (the working
directory by default).

## Runners

cwltool is the default. `--cwl_runner toil-cwl-runner`, or
`run_args_dict={'cwl_runner': 'toil-cwl-runner'}`, runs the same compiled
CWL with Toil. The command Sophios runs is printed, and written to `run.sh` by
`--generate_run_script`. With cwltool:

```text
cwltool_filterlog --disable-pull [--quiet] --provenance autogenerated/provenance/<workflow>
  --write-summary autogenerated/output_<workflow>.json --skip-schemas --relax-path-checks
  --move-outputs --enable-ext --outdir <outdir> [--cachedir <cachedir>] [your flags]
  autogenerated/<workflow>.cwl autogenerated/<workflow>_inputs.yml
```

`cwltool_filterlog` is cwltool, started by Sophios with the log filters that
silence two known-noisy messages; `--skip-schemas` keeps cwltool from
fetching ontology files on every run; `--enable-ext` lets it read cwltool's
extensions, such as the `cwltool:CUDARequirement` a GPU tool declares. With
Toil:

```text
toil-cwl-runner --relax-path-checks --provenance autogenerated/provenance/<workflow>
  --outdir <outdir> --jobStore file:autogenerated/jobStore_<workflow> --clean always
  --noLinkImports --disableProgress [your flags]
  autogenerated/<workflow>.cwl autogenerated/<workflow>_inputs.yml
```

Toil keeps a job store instead of a cache, is never given `--quiet`, and is
not given `--provenance` when your flags mention `slurm`. Both runners run
in-process, and a message cwltool logs about a step names the step as you
wrote it, with the generated id in parentheses:
`[step 2 'append' (greeting__step__2__append)]`.

Flags Sophios does not know go to the runner. On the command line that needs
`--passthrough_flags yes`, and `--run_local` or `--generate_run_script`;
without the first an unknown flag is an error, and without the second
Sophios says the flag would go to a runner this command does not run. In
Python, every key of `run_args_dict` that is not a Sophios option is passed
as `--<key> <value>`: `{'logLevel': 'INFO'}` reaches Toil as
`--logLevel INFO`. A flag that takes no value cannot be passed this way.

## Container engines

`--container_engine` names the engine, `docker` by default; in Python it is
the `container_engine` key. It decides how images are pulled and what the
runner is told:

- `docker`: nothing extra; the runner uses `docker run`;
- `podman`: images are pulled with podman, and the runner is given
  `--user-space-docker-cmd podman`;
- `singularity`: images are pulled as Singularity images into `--pull_dir`,
  and the runner is given `--singularity`;
- any other command: given to the runner as `--user-space-docker-cmd`.

A tool with no `DockerRequirement`, such as `echo.cwl` and `append.cwl`, runs
on the host whatever the engine, and needs its program on your `PATH`.

## Where things land

Everything goes under `autogenerated/`, or under `run()`'s `basepath`:

| Path | What |
|---|---|
| `<workflow>.cwl`, `<workflow>_inputs.yml` | the compiled workflow and its job file, with every relative input path written absolute |
| `<workflow>__step__<n>__<id>/<tool>.cwl` | each step's tool, one directory per step; a subworkflow's directory holds its own tree |
| `<workflow>.names.json` | every generated step id and port name, mapped to what you wrote: workflow, position, name, file and line for a step; the steps and port for a name |
| `outdir_<runner>_<workflow>_<timestamp>/` | the run's output files; `--outdir <dir>` (or the `outdir` key) names it instead, and the directory is made absolute |
| `output_<workflow>.json` | every workflow output with its value: a `File` object or a plain value |
| `provenance/<workflow>/` | the runner's research object: what ran, with what, and the outputs |
| `realtime/`, `<workflow>.realtime.json` | the compiled real-time analyses, when a workflow declares any |
| `run.sh` (in the working directory) | the runner command, from `--generate_run_script` |
| `error_<workflow>.txt` (in the working directory) | the full traceback of a failure Sophios did not expect |

The run ends with `Success! Runner outputs are under <outdir>/`, or with one
`Failure!` line per failed step: the step by name and generated id, how it
ended, what that means when the status is a known one (126: its command could
not be executed; 127: its command was not found, so the tool's `baseCommand`
is not in its image, or not on this machine for a tool without one; 137: it
was killed, usually for memory), and that its own messages are above. When no
step is named, the first `ERROR` line above, or the error the runner raised,
says why. The exit code is the runner's; Ctrl-C exits with 130.

## Caching

`--cachedir <dir>`, or the `cachedir` key, gives cwltool a directory in which
it caches each step's outputs; a later run of a step whose tool and inputs are
unchanged reuses them. There is no cache unless you ask for one, and Toil is
not given it, since it has its job store. A [real-time analysis](realtime-analysis.md)
needs the cache and turns it on, in `cachedir/` unless you named one.

## Quiet and verbose

`--quiet` does two things: it passes `--quiet` to cwltool (never to Toil), and
it gives every tool that declares no `stdout` or `stderr` a `<stem>.out` and
`<stem>.err` to capture them in, which changes the compiled tools. Python
passes `--quiet` to cwltool unless `run_args_dict={'quiet': 'no'}`, and never
adds the capture files. To see each step's command and the runner's own log,
run without `--quiet`, and on the command line pass cwltool's own `--debug`
through with `--passthrough_flags yes` when you need its debug log.

## Environment variables

A tool does not see your shell's environment; cwltool sets `HOME` and
`TMPDIR`, and `PATH` outside a container. A tool that needs a variable
declares it with `EnvVarRequirement`. `Workflow.run(user_env_vars={...})`
adds variables to the environment the runner is started in, for the runner
itself and for tools that run on the host; a key that is not an environment
variable name is `ValueError`.

## Running elsewhere

`--generate_run_script` writes `run.sh`, the exact runner command with
absolute paths, after the pre-flight and the image pulls, and stops. Run it
on this machine later, or read it to see what a run does. The compiled CWL
and job file it names are standard; a CWL runner on another machine needs the
`autogenerated/` tree and whatever the job file points at, and nothing from
Sophios. Sophios also ships a client for a separate compute service, which
takes the compiled workflow and job inputs as they are; see
[The compute client](compute.md).

## Other paths

- `--homedir <dir>` is where Sophios looks for its configuration
  (`<dir>/wic/global_config.json`), your home directory by default; CWL
  clears `HOME` for tools, so a run started from inside one gives it
  explicitly.
- `--pull_dir <dir>` is where Singularity images are pulled.
- `--config_file <file>` names a configuration file to read instead of the
  default; see [Configuration](configuration.md).
